This page is for adding the computers your agents run on and keeping them healthy.

Agents run directly on your own machines, as plain processes of your user, with the machine's tools, files and
network. On fleetd cloud, a team can also run them on [fleetd's computers](/docs/cloud-machines).

A machine needs Linux (x64) or macOS, and the `claude` CLI. Only the hub's owners and admins add, fix or remove
machines.

## The Machines page {#page}

Open **Settings › Hub › Machines**. It has these groups:

- **Machines**: every machine, with a dot (grey when well, amber when it needs you) and what runs there now, or
  what's wrong. Click a row to open its page.
- **What runs where**: **Mac machine**, where Mac screens and iOS simulators run, and **Keep screen recordings for**.
  On a cloud team, **Linux machine** too ([fleetd's computers](/docs/cloud-machines)).
- **Updates**: whether everything is up to date, with **Update** ([Updating](/docs/updating-and-uninstall)).

On the phone, admins find the same groups under **Settings › Machines**.

## Add a machine {#app}

1. Open **Settings › Hub › Machines** and click the **+**.
2. Pick how to reach it:
   - **This computer**: one click. The app installs fleetd here and joins the hub.
   - **A machine the hub can reach**: pick it from the hub's SSH hosts or tailnet, read the plan, then **Add**. Each
     step shows as it runs; **Retry** picks up where a failed step stopped.
   - **Any other machine** (a laptop, or one behind NAT): name it, click **Make the line**, and run that line in a
     terminal on the machine. The line works once, for 15 minutes.
   - **A Mac for agents**: see [The agents' Mac](/docs/agents-mac).
3. The machine shows in the list once it's online.

The new machine must be able to reach the hub's address. A hub that only listens on `127.0.0.1` can't take other
machines: give it a tailnet or LAN address first (`fleetd init --listen <ip>:<port> --url http://<name>:<port>`).

### From the terminal {#cli}

Run these on the hub.

| The machine is | Run |
|---|---|
| Reachable over SSH | `fleetd machine add <ssh-host>` |
| The hub's own computer | `fleetd machine add --local` |
| Anywhere else | `fleetd pair --worker <name>` |

### Over SSH {#ssh}

```sh
fleetd machine add builder-1 --dry-run   # show the plan, change nothing
fleetd machine add builder-1
```

The host can be any name in `~/.ssh/config` or on your tailnet. It's safe to run again: it skips steps already done,
which is also how you repair a machine.

### A machine the hub can't reach {#join}

1. On the hub, run `fleetd pair --worker laptop`. It prints one line.
2. Paste that line into a terminal on the new machine. It installs fleetd and joins.

The code in the line works once, for 15 minutes. `fleetd pair --worker-codes` lists open codes, and
`fleetd pair --worker-revoke <id>` takes one back.

## Log in Claude {#claude}

Agents use the machine's own Claude login (`~/.claude`). If `claude` works in your shell there, it works for fleetd.

To log in from the app:

1. Open the machine's page. Its **Claude** row says it isn't logged in.
2. Click **Log in…**, open the sign-in page on any device and sign in.
3. Paste the code it shows and click **Log in**.

The login stays on that machine; it never reaches the hub or an agent. Or run `claude auth login` on the machine.

### Claude Code's version {#claude-version}

Each fleetd release is tested with one Claude Code version. Updating fleetd moves every machine to it, and fleetd
turns off Claude Code's own auto-update so nothing else moves it. Running sessions finish on the version they started
with.

Claude Code installed with Homebrew or npm isn't moved: the update tells you the command to run.

## Fix a machine {#checks}

The hub checks each machine every 15 minutes. A machine's page lists only what failed, each with its fix:

- **Claude**: not installed at the tested version, or not logged in.
- **Git identity**: commits there don't carry the hub's identity.
- **GitHub access**: git couldn't fetch a bot's repo.
- **Screens**: a kind of screen it could host isn't ready ([Screens](/docs/browser-sessions#settings)).

**Check again** runs the checks now. **Repair**, shown while a machine is offline or degraded, adds it again and
skips what's already in place. A machine that joined with a line gets a new line to run there.

## Remove a machine {#remove}

Click **Remove** on the machine's page, or run:

```sh
fleetd machine remove builder-1
```

This revokes its key and erases its bots (their chats, memory, files and tasks). A machine the hub set up also has
its service stopped and removed.

- `--purge` also deletes fleetd's files on that machine (`~/.fleetd/node`). Your `~/.claude` stays.
- `--force` removes it even while it runs a bot's lead.

For a machine that joined with a line, stop its service there yourself:

```sh
launchctl bootout gui/$(id -u)/sh.fleetd.node
```

## What a machine is used for {#roles}

A machine runs **agents**, hosts **screens** (agents' browsers, emulators and desktops), or **both** (the default).
Change it under **Used for** on the machine's page, or:

```sh
fleetd machine set mac1 --roles sessions --max-sessions 2
```

`sessions` means screens. A machine with screens only runs no agents; it hosts screens for agents on every machine.

## When new agents wait {#guard}

A machine takes no new agents while it's short of disk or its Claude login is nearly out of usage. Running agents
carry on. The bot's status says why.

| New agents wait while | They start again |
|---|---|
| Free disk is below 10% of it, or 20 GB if more | 10% above that |
| A Claude usage window is 90% used | Below 85%, or at the reset |

Change the disk limit with `minFreeGb` in [node.json](/docs/config-and-files#node-json).

### When a Claude login hits its limit {#usage-pause}

Agents that hit their login's limit pause, and go on by themselves at the reset. To go on sooner, click **Resume** on
the bot's status row or in the chat, or run `fleetd usage resume <machine>` on the hub.

## A fair share for each agent {#fair-share}

Agents on one machine share its CPUs, memory and disk:

- **Build jobs**: each agent gets its share of the CPUs (`MAKEFLAGS`, `CARGO_BUILD_JOBS` and similar are set for it).
- **Build slots**: heavy `cargo` builds take turns, one slot per 16 GB of memory, so many agents can't run the machine
  out of memory. Set `buildSlots` in node.json to change it.
- **Heavy-run slots**: agents run each full check, whole test suite or full build as `fleetd-heavy <command>`, which
  takes one of the machine's heavy-run slots, one per 8 cores (at least 2). With every slot in use the run waits its
  turn, first come first served, and says so, so many agents checking at once can't overload the machine or fail each
  other's tests on ports and timeouts. An agent's own small test runs never wait. Set `heavySlots` to change it.
- **Memory cap** (Linux): each agent runs in its own scope, so one runaway process is killed without taking the
  machine down.
- **Scratch space**: each agent's `TMPDIR` is on disk, never in `/tmp`.

## Keep the services running {#service-manager}

On Linux the hub and node run under your systemd user manager. If that manager stops, nothing restarts it until you
log in again. This one-time root command fixes that (replace `dev` and `1000` with `id -un` and `id -u`):

```sh
sudo sh -c "loginctl enable-linger dev && mkdir -p /etc/systemd/system/user@1000.service.d && printf '[Service]\nRestart=always\nRestartSec=5\n' > /etc/systemd/system/user@1000.service.d/fleetd.conf && systemctl daemon-reload"
```

`fleetd init` and `fleetd machine add` run it for you when they can use root without a password. `fleetd doctor`
flags a machine that still needs it.

## When a machine goes down {#down}

A machine shows offline after 45 seconds of silence. If it's still offline after 10 minutes, owners and admins get one
notification, and another when it's back.

## Check health {#health}

```sh
fleetd doctor
```

It checks the hub and every machine, and prints the fix for each problem. See
[Troubleshooting](/docs/troubleshooting).
