You'll add [workers](/docs/glossary#worker), the machines that run agents, and keep them healthy. The hub's owners
and admins add, repair and remove them in the app, and log in their Claude from it too. The [CLI](#cli) does the same
from a terminal on the hub.

A worker needs the `claude` CLI, and Linux on x64 or macOS (Apple silicon or Intel). fleetd has no Linux ARM build
yet.

When your machines are full, [cloud machines](/docs/cloud-machines) on your own boat.dev account can take the overflow;
they show in the same list.

## Add a machine in the app {#app}

Open **Settings › Hub › Machines**. **Add machine** at the top offers three ways, and a fourth for [the agents' Mac](/docs/agents-mac#app), a Mac every project's agents use but none runs on (**A Mac for agents**: a 6-digit code you type in the fleetd app on that Mac):

| The machine is | Pick | What happens |
|---|---|---|
| The computer the app runs on | **This computer** | One click. The app downloads the release of the fleetd version the hub runs, built for this computer, checks it against that release's `SHA256SUMS`, and joins the hub with a one-time code that never shows on screen. The node runs as a user service. An Edge hub asks to be updated first once the edge release has moved past it. On the machine that runs the hub you're connected to, the hub sets it up with its own fleetd instead. A computer that runs another hub, or whose node already belongs to a hub, is left as it is. |
| Reachable from the hub over SSH | **A machine the hub can reach** | Pick it from the hosts the hub sees (its `~/.ssh/config` and its tailnet), and read the plan: the machine's OS and CPU, each step with its command, and notes such as linger. Press **Add**, and watch each step run. |
| Behind NAT, or with no SSH from the hub (a laptop) | **Any other machine** | Give it a name and press **Make the line**. Copy the one line it shows and run it in a terminal on that machine: it installs fleetd and joins with a one-time code. The code works once, for 15 minutes. Under the line, "Waiting for laptop…" turns into "laptop joined." once its node connects; **Open laptop** shows its [checklist](#checklist). |

Adding a machine the hub can reach runs [`fleetd machine add`](#ssh) in the hub, step by step. A failed step shows
its output and what to fix; **Retry** runs it again and skips the steps that finished. The run goes on in the hub if
you leave the page, and Add machine shows it when you come back.

Only a person with Admin on every machine sees Settings' Hub group. Agents' keys can't add or remove machines.

A machine id belongs to one computer. The hub knows each computer by a hash of the id its OS gives it
(`/etc/machine-id` on Linux, `IOPlatformUUID` on macOS), so it never enrolls a second computer under an id that is
already another's, whatever the computer is called. To give an id to another computer, [remove](#remove) the machine
first. The app knows the hub's own computer the same way, wherever the hub keeps its data.

### Repair or remove a machine {#app-repair}

Under Add machine, **This hub's machines** lists every machine with its state, each with **Remove**, and **Repair**
while it is degraded or offline. Open one for its own page: its checklist, then its role, its screens and its max agents.

A machine is degraded while its claude can't run sessions, or while it has no IPv4 network and git there can't reach
GitHub. For the second, a Linux node checks its own network hardware (not Tailscale, docker or loopback) with each heartbeat:
an interface with only a 169.254 link-local address, which is what's left when DHCP times out, counts as none. The
hub shows "no IPv4 network on enp3s0, so GitHub can't be reached" with the fix, `sudo networkctl reconfigure enp3s0`
or `sudo netplan apply`, and its agents keep running. It shows online again at the first heartbeat with an address.

- **Repair** on a machine the hub reaches over SSH (one it set up, its own, or one in its `~/.ssh/config` or tailnet)
  opens its plan in Add machine: adding it again repairs it and skips what is in place. On a machine that joined by
  itself, Repair makes a line that enrolls it again (`--rejoin`): run it on that machine.
- **Remove** asks first, then does what [`fleetd machine remove`](#remove) does: on a machine the hub set up, it stops
  and removes the node's service and revokes its key; on one that joined by itself, it only revokes the key, so stop
  its node there by hand.

### A machine's checklist {#checklist}

A machine's name opens its page, with what it needs to run agents, as the hub's own checks last found it and when.
The hub runs them every 15 minutes, and within a minute of the machine coming back online, going offline or degrading.
**Check again** runs them now.

| Item | Done when |
|---|---|
| Claude | `claude` is installed at the version fleetd was tested with, and logged in. |
| Git identity | The node's commits carry the hub's identity. |
| GitHub access | git could fetch each project's remote at the last agent start there. It waits until an agent has started in one of its projects. |
| Capabilities | What screens it hosts besides browsers: Android, Linux desktop. Each one that's set up but not ready says why. |

An item that wants a look shows its fix: a command to copy, or for Claude's login, **Log in…**.

### Log in Claude from the app {#app-claude}

**Log in…** on the Claude item has the machine's node run `claude auth login`, with the same environment as its
sessions, so the login lands where they read it.

1. Press **Open**, or copy the page's address, and sign in with the Claude account the machine should use. Any device
   works.
2. Paste the code the page shows, and press **Log in**.

Only that code passes through the hub, once, to the node. `claude` keeps the login it gets on the machine; the token
never reaches the hub, the app or any agent's transcript. A login nobody finishes ends after 10 minutes. A wrong or
used code ends it too: press **Try again** for a new page. The machine needs a fleetd recent enough to do this; with an
older one, log in on it [by hand](#claude).

## Add a machine from the CLI {#cli}

Run these on the hub unless it says otherwise.

| The machine is | Use |
|---|---|
| Reachable from the hub over SSH | [`fleetd machine add <ssh-host>`](#ssh) |
| The hub machine itself | [`fleetd machine add --local`](#local) |
| Behind NAT, or has no SSH from the hub (a laptop) | [`fleetd pair --worker <name>`](#join) |

### Over SSH {#ssh}

1. See the plan without changing anything:

   ```console capture=machine-add
   $ fleetd machine add builder-1 --dry-run
   dry run: nothing runs. Planned for a fresh Linux machine at builder-1 (home /home/demo); a real run first reads the machine's state and leaves out what is already done:
   [probe] read the machine's state (read-only)
   [1/5] create fleetd's directories
   [2/5] install fleetd 0.0.0
   [3/5] write the node service
   [4/5] enroll the node with a one-time token (sent on stdin)
   [5/5] (re)start the node
   [hub] wait until builder-1 is online
   [exit 0]
   ```

2. Run it for real:

   ```sh
   fleetd machine add builder-1
   ```

   It copies the hub's own fleetd to the machine, enrolls its [node](/docs/glossary#node), runs the node as a user
   service, and waits until the machine is online. It prints each remote command before it runs it.

   A machine of another OS or CPU than the hub's (a Mac added from a Linux hub, say) gets the same fleetd version
   built for it: the hub downloads that release's build and checks it against the release's `SHA256SUMS` first. A
   machine that has that build already is left as it is. A hub on an Edge build can do this only while the edge release
   is still its build; once it has moved on, the add stops and says to update the hub first.

The host name can be anything in `~/.ssh/config` or on your tailnet. You can also run `fleetd init` again and pick the
machine from a list.

It is safe to run again: a real run reads the machine's state first and skips what is done.

It never takes over another fleetd's node. When the user's systemd manager already runs `fleetd-node.service` from
another home (the same account with another `HOME`, say), adding or joining stops before it changes anything and says
so. Pass `--no-service` to enrol the node without a service, and start it with the command it prints.

### The hub machine {#local}

```sh
fleetd machine add --local
```

The same steps, run on this machine without SSH. `fleetd init` does this when you pick "(this machine)". Run it again
to repair the hub machine's node.

### A machine the hub can't reach {#join}

1. On the hub, print a join command for the new machine:

   ```sh
   fleetd pair --worker laptop
   ```

   Expected output:

   ```text
   On laptop, run:

     curl -fsSL https://fleetd.sh | sh -s -- --join http://hub.your-tailnet.ts.net:4790 --code <code> --machine-id laptop --git-identity 'ada-lovelace <1234567+ada-lovelace@users.noreply.github.com>'

   The code works once, until 2026-10-18T13:35:46.366Z. laptop needs claude installed and must reach the hub at that address.
   ```

2. Paste the printed command into a terminal on the new machine. It installs fleetd and joins the hub with that
   address and code, without asking for them. Where fleetd is already installed and `fleetd init` asks what the
   machine is, pick **A worker** and paste the same line: it takes the hub, the code, the machine's name and the
   commit identity from it.

The code works once, for 15 minutes. The new machine must reach the hub's address. A hub that is only at
`127.0.0.1` or `localhost` gives a line that works on its own computer alone; `fleetd pair --worker` and Add machine
say so. Give the hub its tailnet or LAN address first: on the hub, `fleetd init --listen <ip>:<port> --url http://<name>:<port>`.

A machine has one code that works at a time: printing a new one replaces the machine's open code.

To see the codes that still work, run `fleetd pair --worker-codes`. It lists each code's id, machine, when it was
made and when it expires, but never the code itself. To take one back before it is used, run
`fleetd pair --worker-revoke <id>`. The hub drops used and expired codes a day later.

To repair the worker later, run the same command again. `--rejoin` enrolls it again with a new code.

A node keeps the machine id it joined with. The hub refuses to enroll a node home (its key in `node-key.pem`)
already enrolled under another id, since that would put all its projects and chats on a second machine. To repair it, rejoin it under its own id: run `fleetd pair --worker <id>` on the hub and the line it prints.
To give it a new id, remove the old machine first (`fleetd machine remove <old id>`), then join under the new one.

If the hub refuses the join (a spent code, say), the machine stays as it was: its node keeps its settings, and its
service starts again.

## Log in Claude on a worker {#claude}

Sessions use the worker's own claude setup in `~/.claude`. If `claude` works in your shell there, it works for
fleetd: your login, a proxy in `~/.claude/settings.json`, and your MCP servers.

If it isn't logged in, log it in [from the app](#app-claude), or on the worker as you normally do:

```sh
claude auth login
```

Behind a proxy, log in through your proxy instead. To give a worker's sessions their own claude profile, see
[The Claude login](/docs/config-and-files#claude).

### Claude Code's version {#claude-version}

Each fleetd release is tested with one Claude Code version. Updating fleetd moves every machine's Claude Code to that
version (see [Update](/docs/updating-and-uninstall#everything)), and nothing moves it on its own:

- The node turns Claude Code's own background update off when it starts, by setting `"DISABLE_AUTOUPDATER": "1"`
  in the `env` of the `settings.json` its sessions read (`~/.claude/settings.json` unless the machine has its own
  profile). That covers a `claude` you run yourself on that machine too. `fleetd doctor` warns when it is on.
- Sessions that are already running finish on the version they started with. New sessions start on the new one.
  Nothing waits for the machine to be idle.
- Only Claude Code's native install (`~/.local/bin/claude`) is moved. A Homebrew, npm or package install, or a
  machine without claude, is left as it is: the update says so in a calm line with the command that updates it
  (`brew upgrade claude-code`, say), not as a failure.

## Remove a machine {#remove}

In the app, press **Remove** beside it in [Settings › Hub › Machines](#app-repair). From the CLI:

```sh
fleetd machine remove builder-1
```

It stops and removes the node's service on that machine, revokes its key on the hub, and forgets everything the hub
held of it, keyed by its id: its sessions, checkouts, settings and slots, and its projects, each erased as deleting it
would: its chat, memory, skills, files, orders and tasks. A machine that joins again under the same id starts its
projects afresh. Another machine's rows stay, even under the same project ids. The factory metrics stay as history,
until their own retention prunes them. Open apps drop the machine and its projects at once. A node that is still linked
is cut off at its next heartbeat (within 15 s), and what it reported in the meantime is forgotten too. To clear what an older fleetd's remove left behind, run the same
command again. The projects it left are also listed under **Left from removed machines** in Settings › Hub ›
Machines, each with Remove, and Delete in Settings › Projects works for them too: no machine holds their files, so
either only forgets the project in fleetd. The hub never forgets them on its own.

| Option | Also does |
|---|---|
| `--purge` | Deletes `~/.fleetd/node` and `~/.fleetd/claude.env` on that machine. Your own `~/.claude` stays. |
| `--force` | Removes it even while it runs projects' leads. |

A machine that runs projects' leads, or one the app is still adding, isn't removed. Removing it would stop those leads
or undo the add halfway. The refusal names the projects, and says how to repair the machine instead
(`fleetd pair --worker <id>` and the line it prints, with `--rejoin`). To remove it anyway, press **Remove anyway** in
the app, or pass `--force`.

For a machine that joined with `fleetd pair --worker`, only the key is revoked:

```text
laptop was not set up by fleetd machine add from this hub, so only its key is revoked here; stop its node by hand.
revoked laptop's node key; the hub refuses that node from now on.
erased laptop's 2 projects: their chats, memory, skills, files, orders and tasks.
the hub forgot laptop's sessions, checkouts and settings (214 rows); the factory metrics stay as history.
```

Stop its node on that machine yourself:

<Tabs syncKey="os">
<TabItem label="macOS">

```sh
launchctl bootout gui/$(id -u)/sh.fleetd.node
```

</TabItem>
<TabItem label="Linux">

```sh
systemctl --user disable --now fleetd-node.service
```

</TabItem>
</Tabs>

## Disk and usage {#guard}

A machine short of disk, or whose Claude login is nearly out of a usage window, takes no new agents until it has room
again. Agents already running keep going. The node reads the figures every 15 seconds, with its heartbeat.

CPU load and memory in use never hold new agents back. New agents start by fixed rules: they wait only for a free
place under the [agent caps](/docs/projects#max-agents), and their builds wait for the machine's
[build slots](#fair-share), sized to its memory.

| New agents wait while | They start again at |
|---|---|
| Free space where the worktrees live is below `minFreeGb` in [`node.json`](/docs/config-and-files#node-json): 10% of the disk or 20 GB by default, whichever is larger. | 10% above it. |
| A usage window of the machine's Claude login is 90% used, or claude warned about it without a figure. API keys and gateways report no windows. | Below 85% or at the window's reset. A reading with no reset time counts for 15 minutes. |

The project's status says why, for example "Paused new agents: 14 GB free on builder-1" or "Paused new agents: 5-hour
limit 91% on builder-1 as of Tue 13:42 UTC, resets Tue 14:00 UTC (pauses at 90%, lifts below 85%)", and `fleetd doctor`
shows each machine's free space. A writer's worktree, build output included, goes once its PR merges, unless it holds
uncommitted or unpushed work. A reader's or reviewer's goes when its task ends. When `sccache` is on the node's `PATH`,
sessions compile through it, so a dependency builds once per machine rather than once per worktree: a new worktree's
first check skips most of its dependencies' compiles. The cache is sccache's own, `~/.cache/sccache` (10 GB at most
unless `SCCACHE_CACHE_SIZE` says otherwise); fleetd's own dependencies take about 350 MB of it.

## When a Claude login hits its limit {#usage-pause}

When agents on one machine hit their Claude login's usage or rate limit, fleetd parks them and pauses new turns on that
login. They go on by themselves at the reset claude's message named, or as soon as a turn on that login completes. The
project's Status row and its chat say so, with **Resume**.

To go on sooner, once the login has capacity again:

- In the app, press **Resume** on the project's Status row or on the chat's blocked line. Your device key needs
  operate on the machine (a paired app has it).
- On the hub machine, run `fleetd usage` to see each machine's pause, and `fleetd usage resume <machine>` to lift
  one. Neither needs a key or `--hub`: they use the hub's own CLI key and reach the hub at the address it listens on.
  From elsewhere, add `--hub <url> --key-file <path>`.

Resume sends every parked agent "continue". An agent whose login is still limited parks again on its next turn, with
the real reset. Whenever the lead takes a turn during the pause (you message it, say), its wake states the pause,
when it ends and that you can press Resume. It can lift the pause on its own project's machine with `usage_resume`, at
most once every 10 minutes, and that is recorded as the lead's.

## A fair share for each agent {#fair-share}

Agents on one machine share its CPUs, memory and disk. Each session gets:

| What | How |
|---|---|
| Build jobs | Each agent's share of the CPUs: the CPUs divided by the agents the machine fits, at least 2. fleetd sets `CARGO_BUILD_JOBS`, `MAKEFLAGS=-j<n>`, `CMAKE_BUILD_PARALLEL_LEVEL` and `GOFLAGS=-p=<n>`, and vitest's `VITEST_MAX_WORKERS` to `<n>` but at least 4, except any you set in `claude.env`, and a task's brief says what each is. |
| Build turns | Agents' cargo builds take turns for the machine's build slots, so twenty agents compiling at once can't run it out of memory. A `cargo` of fleetd's own comes first on each agent's `PATH` (`~/.fleetd/node/build-slots/bin`) and hands every command to the real one; `build`, `check`, `clippy`, `test`, `bench`, `doc`, `rustc`, `install`, `fix`, `nextest`, `llvm-cov` and `miri` first take a slot, and hold it until they end. `cargo run` takes one for a `cargo build` of what it runs, then lets it go before the program starts, since that may run for hours. Other commands (`fmt`, `metadata`, `tree`) start at once, and so does a call that compiles nothing: `cargo -V`, a command's own `--version` or `--help` (`cargo nextest --version`), `cargo install --list`. A build takes one slot, and two when it builds a lib's tests beside the lib, a package's two biggest rustc at once: a `cargo test`, `nextest` or `llvm-cov` naming neither `--lib` of one package nor only other targets (`--test <name>`, `--doc`), or a `cargo build --all-targets`. With too few slots free, a build queues first come first served and prints one line, such as `fleetd: queued for a build slot (1 build ahead; 4 slots on this machine): it starts once one frees`. A running build is never stopped, and a slot frees the moment its build ends, however it ends. Slots: one per 11 GB of memory left after a quarter of it (4 to 16 GB) is kept for the system, at least 1: 11 GB holds fleetd's lib tests, the biggest rustc measured, so every slot busy still fits. A 16 GB laptop gets 1, a 32 GB one 2, the 60 GB devbox 4. Set `buildSlots` in node.json to change it (no restart needed), or `0` to turn turns off. A task's brief says how many. |
| Language servers | Claude Code's heavy language servers (rust-analyzer, clangd, the Java and Kotlin ones) are off in every session: each holds gigabytes per worktree outside the build slots. A project's `HEAVY_LANGUAGE_SERVERS=1` variable turns them back on. See [Heavy language servers are off](/docs/what-agents-are-told#language-servers). |
| Scratch space | `TMPDIR`, `TMP`, `TEMP` and Claude Code's `CLAUDE_CODE_TMPDIR` point at `~/.fleetd/node/tmp/<16 hex characters, one per session>`, on disk. Never `/tmp`, which is often held in memory. It goes with the writer's worktree; for a session without one, when the session is stopped, or when the node restarts and the session didn't run on through it. |
| Its own memory scope (Linux) | When the node can reach your systemd user manager, each session runs in its own transient scope (`systemctl --user list-units 'run-*.scope'`, described as "fleetd agent …"). If memory runs out, the kernel's kill lands in one agent: the build it killed fails, and the agent sees the error and goes on. The scopes and the node's unit have `OOMPolicy=continue`, so an out-of-memory kill never fails an agent's scope or the node. A lead's and an agent's scope isn't part of the node's unit: restarting the node leaves them running, and the node picks them up again when it starts. One whose node doesn't come back within 15 minutes ends by itself, and `fleetd machine remove` ends them at once. If a scope can't be started, the session starts without one, and the node checks again 10 minutes later. Without a user manager (macOS, containers), sessions run as before. |

A node unit written before this has no `OOMPolicy=continue`; run `fleetd machine add` again on that machine to rewrite
it.

## When work goes to a cloud machine {#cloud}

A hub with cloud machines (boat.dev machines the hub keeps asleep and wakes when work needs them) sends work there
only when the project's own machine is at its agent limit: its [max agents](/docs/projects#max-agents), or no disk room
for another agent. Memory, load and pressure never send work to the cloud; to burst sooner, lower the machine's max
agents. Placement is the same every time, in this order:

1. **The project's own machine**, while it has room.
2. **An awake cloud machine with room**: the one running the most agents, so work packs onto it and the others go
   idle and stop.
3. **A sleeping cloud machine is woken**, within fleetd's start budget and the day and month budgets. One wakes at a
   time; the next wakes only once that one is awake and full.
4. **Otherwise the task waits** for whichever frees first, and its queued line says why.

A task may go to a cloud machine only when all of these hold:

- Cloud machines are on, and the hub has checked boat.dev since it started.
- Its project is opted in to cloud machines.
- Its project has no secret variables (those are kept only on its own machine). Plain variables,
  the worktree setup and the project's rules come from its own machine's checkout.

A fleet cap, or a max agents a person set for the project, holds bursting too: a project set to 6 runs 6 in all,
wherever they run.

Each cloud machine keeps a clone of each opted-in project's repos, made when it first wakes after the project opted
in. It never shows as a project of its own. A private repo clones with the token of the hub's
[GitHub App](/docs/github) for it. Later fetches there use the GitHub token of the order whose task launches there.
Both are handed to git in its environment for github.com only, never written to the clone's config. A repo the App
doesn't reach clones only if it is public. When a clone fails (no access, no remote, its folder taken), that machine
tries it again after 10 minutes, then doubling up to 6 hours. Meanwhile its tasks say why in their queued line, and
no cloud machine wakes for them.

**Follow-ups stay where the work is.** A task placed on a cloud machine records it, and every later turn (a CI fix, a
review fix, a lead's message, a resume after its run died) runs on that machine, in the same worktree. If the machine
is asleep, the follow-up wakes it and waits, even when its own machine has room. If it can't wake (a budget is spent,
the start budget is used), the task waits there and its lead is told once.

**Screens** go to an awake cloud machine only when every other machine's screen slots are full, the busiest one first.
A screen never wakes a cloud machine. An agent on a cloud machine gets its screens there, as on any machine.

The queued line puts the project's machine first, then the cloud's part:

| Line | Meaning |
|---|---|
| machine cap: 6 of 6 running on devbox (set); waking boat-2, a cloud machine, about 30 s | A cloud machine is waking for it. |
| …; the cloud machines are busy (3 of 3 awake) | Every cloud machine is awake and full. |
| …; cloud paused: today's boat.dev budget ($3.00) is spent; work runs on your own machines when there's room | No cloud machine takes new work until the budget allows it. |
| …; fleetd's boat.dev start budget is used (6 of 6 this minute): next start at 14:32 | No more wakes until then. |
| …; not for cloud: its project's secret variables are only on its own machine | This task may not go. |
| …; its repo didn't clone on boat-1, a cloud machine (…); tried again at 14:40 UTC | No cloud machine takes or wakes for it until then. |
| waiting for boat-2 to wake: its work is there | A follow-up waking its own cloud machine. |

The lead's list of tasks shows "on boat-2, a cloud machine" for a task running there.

## Machine roles {#roles}

Each machine runs **agents**, hosts **screens** (an agent's [browser, emulator or desktop](/docs/browser-sessions), or the agents' Mac's screen),
or **both**, the default. An owner or admin sets it on the machine's own page in **Settings › Hub › Machines** (open it
from the list), or with an admin key, where the screens role is named `sessions`:

```sh
fleetd machine set mac1 --roles sessions --max-sessions 2
fleetd machine set devbox --roles agents,sessions --max-sessions auto
```

- **Agents only.** The machine hosts no screens. Its agents' screens run on a machine that does.
- **Screens only.** The machine runs no agents: those running finish their work, and its projects' agents wait until
  it runs agents again. It hosts screens for agents on every machine.

Screen slots are counted apart from agent slots. A machine hosts at most its screen cap at once: what it fits (one
screen per two CPUs and about 2 GB of memory each, at most 16, and never fewer than its agent slots and leads), or
the number you set, 1 to 64.

Each node reports what it can host, in plain words, and the Screens part of the machine's page shows it, with a switch
per kind that turns it on or off there ([Turn screens on in Settings](/docs/browser-sessions#settings)):

| Kind | Needs |
|---|---|
| Browser | Chrome: the node's own, which it installs as it starts, or the one `browser.chrome` names in node.json. |
| Android emulator | fleetd's own pinned emulator: Linux on x86_64, opted in with `"device": {"enabled": true}` in node.json (the first screen installs it) or installed already, and a `/dev/kvm` this user can open read-write. See [Android screens](/docs/browser-sessions#android-setup). |
| Desktop | Linux with docker, podman or Xvfb. |
| Agents' Mac | [The agents' Mac](/docs/agents-mac): the node's account at the Mac's screen (yours is fine), unlocked, with Accessibility and Screen Recording. Elsewhere it says `Needs a Mac`. The agents' Mac hosts only this kind. See [the agents' Mac's screen](/docs/browser-sessions#mac). |

When an agent starts a screen, the hub places it: on the agent's own machine when it hosts screens, can run that kind
and has a free screen slot; else on the online machine that can with the most free slots. When none can, the agent is
told why in one line: none can host that kind, the ones that can are offline, or every one is full. The default cap is
never lower than the machine's agent slots and leads together, one screen each, as before screen caps. A screen a
person [opens themselves](/docs/browser-sessions#yours) takes a slot too, on the machine they pick, and a person
waiting for a full machine's next slot gets it before any agent does.

A screen on another machine works as one on the agent's own:

- **Its secrets go sealed.** Before it starts, the agent's node seals the screen's secrets (its project's, its
  order's and its MCP servers') to the hosting machine's key, as the app seals a secret to a machine. The hub passes
  the box on and can't open it. The hosting machine scrubs the screen's action log and page snapshots with them,
  as for a screen of its own, and forgets them once the screen has started.
- **Its 1Password token stays home.** A `fill_credential` is read from 1Password on the agent's machine, with its
  token, and only the value goes to the hosting machine, sealed to it. That machine fills it into the item's own sites
  only, refuses reads of it as for a fill of its own, and wipes it. The agent's machine masks it in its agent's
  reports.
- **Its relay is encrypted end to end.** The agent's `agent-browser` reaches the browser through a relay on the hub.
  The agent's node connects with a token only that node and the hub know (the hub keeps just its SHA-256). The two
  nodes encrypt every message with a key sealed along with the secrets, so the hub carries only ciphertext, and it
  logs none of it.
- **Its steps are recorded there.** Each `agent-browser` command that drove it goes into the hosting machine's
  recording, with the page after it, masked on the agent's machine first.
- **Agents' iOS simulators are on [the agents' Mac](/docs/agents-mac)**, reached with `mac`, not as screens.
  Android screens stay on their agent's machine for now.

Only machines whose fleetd seals and opens these boxes take part. An agent on a machine with browser screens turned
off can't start one anywhere: it has no proxy to drive it through.

## Check health {#health}

```sh
fleetd doctor
```

It checks the hub and every machine: online (or degraded, with its claude's or its network's cause), claude version
and login, commit identity, disk space and the usage breaker. Each problem comes with the command that fixes it.

Every finding and its fix: [Troubleshooting](/docs/troubleshooting).
