Find the problem `fleetd doctor` reported, or why work is stuck, and fix it. `fleetd doctor` checks the
[hub](/docs/glossary#hub) and every [worker](/docs/glossary#worker).

## Run the doctor {#doctor}

On the hub:

```sh
fleetd doctor
```

Example output, from a new hub with one worker, `test-1`, where nothing is logged in yet:

```text
✗  doctor hub gh is not logged in on the hub; the merge train and PR checks need it. Fix: gh auth login
!  doctor test-1 test-1 is degraded: claude is not installed (claude not found). Fix: curl -fsSL https://claude.ai/install.sh | bash
✗  doctor test-1 claude is not installed on test-1; its sessions can't start. Fix: curl -fsSL https://claude.ai/install.sh | bash
!  doctor test-1 test-1's node could not tell whether its claude is logged in
!  doctor test-1 test-1's node has not probed its claude yet
✗  doctor test-1 No git commit identity is set on test-1. Fix: git config --global user.email '<id>+<user>@users.noreply.github.com'
✓  doctor 4 of 10 checks pass
[exit 1]
```

Each line names where the problem is: `hub`, or a machine. Checks that pass aren't listed, only counted on the last
line.

| Mark | Means |
|---|---|
| ✗ | A failure. Fix it. |
| ! | A warning, or a check that couldn't tell. |
| – | Not checked yet. |
| ✓ | Only on the last line: how many checks passed. |

Most findings end with `Fix:` and what to do, on the machine the finding names. The app's Machines screen shows the
same checks. The tables below give each check's id in brackets, such as `[claude_login]`.

## The hub {#hub}

| Symptom | Cause | Fix |
|---|---|---|
| "the hub does not answer at `http://…`" `[exit 4]` | The hub isn't running. | `fleetd init`. If you run the hub yourself (`--no-service`): `fleetd hub start`. Log: `~/.fleetd/hub/hub.log`. |
| "The hub does not answer at its own address …/healthz" `[reachable]` | The hub service is stuck. | [Restart the hub service](#restart). |
| "gh is not logged in on the hub" `[gh_auth]` | `gh` is missing or logged out. | `gh auth login`. If `gh` is missing, install it from [cli.github.com](https://cli.github.com) first. |
| "The hub's address `http://…` is not HTTPS" `[https]` | The hub listens on plain HTTP outside loopback or a tailnet. | Serve it over HTTPS, then point fleetd at it (below). |
| "No CI on owner/repo: fleetd merges only on green CI, so their ready PRs wait." `[repo_ci]` | The repo has no GitHub Actions workflow and requires no check, so its reviewed PRs can't go green. | Add a workflow that runs on pull requests. The waiting PRs go on by themselves once it exists. |
| "The hub has no address set up", or `setup.json` is unreadable `[https]` | `~/.fleetd/hub/setup.json` is missing or broken. | Same as above: `fleetd init --url <https address>`. |
| "… has no hub set up" `[exit 4]` | The hub was started by hand without `fleetd init` first, so its home has no `setup.json`. | Run the fix it prints. For a hub you run yourself, that is `fleetd init --no-service --home <home> --listen <host:port>`, which leaves the running hub alone. |

This is what doctor shows when the hub is down:

```console capture=doctor-no-hub
$ fleetd doctor
✗  doctor the hub does not answer at http://127.0.0.1:4778: error sending request for url (http://127.0.0.1:4778/mcp): client error (Connect): tcp connect error: Connection refused (os error 111). Fix: fleetd init (it starts the hub and repairs its setup)
[exit 4]
```

To serve the hub over HTTPS with Tailscale, stop the hub, then:

```sh
tailscale serve --bg 4790
fleetd init --url https://<that address>
```

Plain HTTP is accepted on loopback and on a tailnet address (`100.64.0.0/10` or a `*.ts.net` name). If the HTTPS
address stops answering, check where it points with `tailscale serve status`.

## Claude {#claude}

These apply to every worker.

| Symptom | Cause | Fix |
|---|---|---|
| "claude 2.1.302, not logged in, so its sessions can't start" `[claude_login]` | `claude` on that machine is logged out, or its login expired. | `claude auth login` on that machine, or log in through your proxy. |
| "claude is not installed on laptop" `[claude_version]` | No `claude` on the machine's `PATH`. | `curl -fsSL https://claude.ai/install.sh \| bash` |
| "claude 2.1.296 is older than fleetd is tested with" `[claude_version]` ! | An older `claude`. It may work: fleetd checks its protocol at every start. | `claude update` |
| "claude 2.2.0 is newer than fleetd is tested with" `[claude_version]` ! | A `claude` past fleetd's tested range. Sessions run. | If they misbehave, `claude install 2.1.302` |
| "`claude --version` printed …, which fleetd can't read" `[claude_version]` | A broken install. | `curl -fsSL https://claude.ai/install.sh \| bash -s 2.1.302` |
| "did not answer fleetd's protocol probe as expected" `[runner_conformance]` | This `claude` speaks a different protocol. | `claude install 2.1.302` |
| "`claude --version` and the running claude disagree" `[runner_conformance]` | Two `claude` installs on `PATH`. | Reinstall with `curl -fsSL https://claude.ai/install.sh \| bash`, and remove the other. |
| "has not probed its claude yet" `[runner_conformance]` | The node just started. | Nothing: it clears by itself. |
| An agent's activity says "claude offered its own agent tools (…)" | A newer `claude` has an agent tool fleetd's deny list didn't name. fleetd stopped that session, and the next start denies the tool. | Nothing. If it happens again, `claude install 2.1.302`. |

fleetd is tested with claude `>=2.1.300, <2.2.0`; other versions run, with a warning. A machine whose claude is
missing or logged out runs no sessions until it is fixed. fleetd turns claude's auto-updater off for its own sessions.

## Machines {#machines}

| Symptom | Cause | Fix |
|---|---|---|
| "laptop is offline (last seen …)" `[online]` | The node is down, or the machine is asleep or off the network. | Wake it, then [restart the node](#restart). Log: `~/.fleetd/logs/node.log`. |
| "laptop is degraded: …" `[online]` | Usually a claude problem on that machine. | The fix the finding names: see [Claude](#claude). |
| "No git commit identity is set on laptop" `[commit_identity]` | The node has no commit author. | Set up over SSH: `fleetd machine add laptop`. Joined with a code: `fleetd pair --worker laptop`, then run what it prints on laptop. The hub machine: `fleetd machine add --local`. |
| "Commits on laptop use … ; the hub's identity is …" `[commit_identity]` | The machine's git config differs from the hub's. | Same as above. |
| "Paused new agents: 14 GB free on laptop" `[disk]` | Low disk where the worktrees live. Each writer gets its own git worktree and build output. | Free space on that disk. New agents start again by themselves once it has room. See [Disk and load](/docs/machines#guard). |
| "Paused new agents: load 70.2 on 32 CPUs on laptop" `[disk]` | The machine is overloaded. | Nothing: new agents start once the load falls. |
| "New turns on laptop are paused by the usage breaker" `[usage_breaker]` | Its Claude login hit a plan or rate limit. | Wait for the reset (the finding says when), or, once it has capacity, call `usage_resume` from an [MCP client](/docs/mcp-clients). |

### Keep a machine awake {#sleep}

While agents run, the node keeps its machine awake. Between jobs nothing does. Sleep on battery only is fine.

| Desktop | Fix |
|---|---|
| macOS | `sudo pmset -c sleep 0` |
| GNOME | `gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-type 'nothing'` |
| KDE Plasma | System Settings > Power Management > On AC Power > When inactive: Do nothing |
| logind `IdleAction` | `IdleAction=ignore` in `/etc/systemd/logind.conf.d/fleetd.conf`, then reboot |

When a machine wakes, its node reconnects at once, resumes any run that went quiet, and the machine strip shows
"slept 10m46s" for a while.

## Restart a service {#restart}

<Tabs syncKey="os">
<TabItem label="macOS">

```sh
launchctl kickstart -k gui/$(id -u)/sh.fleetd.hub     # the hub
launchctl kickstart -k gui/$(id -u)/sh.fleetd.node    # a node, on that machine
```

</TabItem>
<TabItem label="Linux">

```sh
systemctl --user restart fleetd-hub.service     # the hub
systemctl --user restart fleetd-node.service    # a node, on that machine
```

</TabItem>
</Tabs>

| Log | Where |
|---|---|
| Hub | `~/.fleetd/hub/hub.log`. Run by hand: the terminal. |
| Node | `~/.fleetd/logs/node.log`. Run by hand: the terminal. |
| The desktop app | `~/Library/Logs/fleetd/app.log` on macOS, `~/.local/state/fleetd/app.log` on Linux. Help → Reveal Logs opens it; Help → Copy Diagnostics copies the app's version, the OS, the hub connection and the log's last lines, for a bug report. |

## Work is stuck {#stuck}

Ask the lead in the chat what it is waiting on. `fleetd status` with the project shows its state, why it is blocked
and why its bar last fell:

```sh
fleetd status storefront
```

| Symptom | Cause | Fix |
|---|---|---|
| A pull request stays queued on the [merge train](/docs/glossary#merge-train) | CI or a review is pending, or the train can't read GitHub. | The `train_get` tool shows each PR on the train with its state and last error. |
| An agent's activity says "node retry 1/3 in 57 s: overloaded" | Claude's API was overloaded or the network failed, after claude's own retries. | Nothing. The node continues the same run after about 1, 4 and 15 minutes, then fails it with claude's words. |
| Your message waits and the chat says why | The lead can't start: `claude` logged out, out of range, or the worker offline. | See [Claude](#claude) and [Machines](#machines). |

Then check the logs (above) for the hub and the project's worker.
