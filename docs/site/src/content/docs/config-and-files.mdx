Where fleetd keeps its files, and the settings you can change by hand. Most people never need this page: the app
covers the same settings.

## Where things live {#home}

Everything is under `~/.fleetd`. `fleetd uninstall` keeps it all.

```text
~/.fleetd/
  bin/fleetd            the CLI
  claude.env            optional extra environment for every claude
  logs/node.log         the machine's log
  hub/                  the hub (hub machine only)
    hub.sqlite          everything the hub knows
    hub.log             the hub's log
    setup.json          what fleetd init set up
    cli.key             the key the CLI on this machine uses
    memory/             what the leads remember, as markdown
    prompts/            your edited prompts
    skills/             skills, hub-wide and per bot
    attachments/        files sent in chats
  node/                 the machine's own part (every machine)
    node.json           its settings
    node-key.pem        proves the machine to the hub
    sessions.sqlite     its sessions
    worktrees/          one git worktree per agent
    tmp/<id>/           each agent's scratch folder
    project-env/        bots' variables and secrets (mode 0600)
    claude-accounts/    Claude keys sealed to this machine (mode 0600)
```

## Memory files {#memory}

What the leads remember is plain markdown in `~/.fleetd/hub/memory`:

- `people/<person id>.md`: how one person works, with their topic files in `people/<person id>/`.
- `<machine>/<bot>/MEMORY.md`: one bot's memory, with its topic files beside it.

Each line starting with `- ` is one entry. Edit them in Settings › a bot › Instructions & memory, or by hand on the
hub. The files stay the truth: the app rewrites them on every change.

## Logs {#logs}

- **Services** (set up by `fleetd init` or `fleetd machine add`): the hub logs to `~/.fleetd/hub/hub.log`, each
  machine to `~/.fleetd/logs/node.log`.
- **By hand** (`fleetd hub start`, `fleetd node join`, `fleetd node run`): the terminal.
- **The desktop app**: `~/Library/Logs/fleetd/app.log` on macOS, `~/.local/state/fleetd/app.log` on Linux. Help ›
  Reveal Logs opens it. It holds errors only, never keys or message text.

## node.json {#node-json}

Each machine's settings, in `~/.fleetd/node/node.json`. `fleetd node join` and `fleetd machine add` write it.
Restart the node after a change (`fleetd node restart`), except where a key says otherwise.

- `hub`: the hub's address.
- `machineId`, `name`: how the hub knows this machine.
- `cmdRoots`: folders the machine may run commands in. Default: your home folder.
- `claudeConfigDir`: a separate Claude Code profile for this machine's sessions ([below](#claude-profile)).
- `minFreeGb`: new agents wait while the disk has less free than this. Default: 10% of the disk or 20 GB,
  whichever is larger. `0` turns it off. No restart needed.
- `buildSlots`: how many agents' cargo builds run at once; the rest wait their turn. Default: one per 16 GB of
  memory. `0` turns it off. No restart needed.
- `heavySlots`: how many heavy runs (agents' full checks, whole test suites, full builds) run at once; the rest
  wait their turn. Default: one per 8 cores, at least 2. `0` turns it off. No restart needed.
- `warmBuilds`: finished cargo builds kept for the next reader or reviewer of a repo. Default: 2. `0` keeps none.
- `browser`, `device`, `desktop`, `mac`, `ios`, `agentsMac`: which [screens](/docs/browser-sessions) the machine
  runs. Set these in Settings › Hub › Machines rather than by hand.

## Claude Code login {#claude}

Agents run `claude` with your own Claude Code setup on that machine (`~/.claude`). Your login, the `env` in
`~/.claude/settings.json`, an `apiKeyHelper` and your MCP servers all work as in your own terminal.
`fleetd doctor` shows the version and login each machine uses.

fleetd adds its own tools and settings on top. [Agent tools](/docs/reference/agent-tools) lists them.

### A separate profile {#claude-profile}

To give a machine's agents their own Claude Code profile:

1. Set `"claudeConfigDir": "<dir>"` in that machine's `node.json`, or join with
   `fleetd node join --claude-config-dir <dir>`.
2. Restart the node.

A session can only resume under the profile it started in.

## claude.env {#claude-env}

Optional `KEY=VALUE` lines in `~/.fleetd/claude.env`, added to every `claude` fleetd starts on that machine. Use it
for a variable your login needs that services don't see. Keep it mode `0600`.

```ini
CLAUDE_CODE_OAUTH_TOKEN=<token from claude setup-token>
# or
ANTHROPIC_BASE_URL=https://gateway.example.com
ANTHROPIC_AUTH_TOKEN=<token>
```

- It is read again at each session start.
- `#` comments, blank lines and `export ` are allowed.
- The `env` in `~/.claude/settings.json` wins over it.
- An agent on a [Claude account](/docs/people#claude) uses that account instead.

## .fleetd/policy.yaml {#policy}

An optional file in a bot's repo that adds tool rules for its agents. fleetd reads it from the bot's checkout, so a
change applies within a minute, committed or not.

```yaml
tools:
  allow: ["Bash(npm test:*)"]
  deny: ["Bash(git push:*)"]
branchPrefix: team-a/
```

- `tools.allow`, `tools.deny`: Claude Code permission rules for every session. Deny wins.
- `branchPrefix`: what agents' branches start with. Default `fleetd/`. Must end in `/`.

A broken file is refused with the exact problem, never ignored, so a typo can't drop a deny rule.

## .fleetd/pre-push.json {#pre-push}

An optional file in a repo naming a check that fleetd's writers must pass before they push.

```json
{
  "check": "scripts/check.sh",
  "background": "scripts/check.sh --background",
  "wait": "scripts/check.sh --wait"
}
```

1. A writer runs `check`. For a long check, it starts `background` and waits on `wait`, a command that ends when the
   check does.
2. When the check passes, it records the tree it checked:

   ```sh
   tree=$(git write-tree)   # with everything it checked staged
   echo "$tree" >>"$(git rev-parse --git-path fleetd-checked)"
   ```

3. fleetd refuses a writer's push of any other tree, with what to do. `--no-verify` doesn't get around it.

On a fleetd machine, writers run `fleetd-heavy <check>`, or `fleetd-heavy <background>` then `wait`, so the check
waits for one of the machine's [heavy-run slots](/docs/machines#fair-share). The `background` start and the `wait` take
no slot of their own, so a check with a `background` command should take its slot itself, as fleetd's does:

```sh
if [ -z "${FLEETD_HEAVY_SLOT:-}" ] && command -v fleetd-heavy >/dev/null; then exec fleetd-heavy "$0" "$@"; fi
```

Only fleetd's writers are held to it. Your own pushes and the merge train's work as before.

## Services {#services}

`fleetd init` and `fleetd machine add` run the hub and each machine as user services:

<TabItem label="macOS">

- Machine: `~/Library/LaunchAgents/sh.fleetd.node.plist`

</TabItem>
<TabItem label="Linux">

- Hub: `~/.config/systemd/user/fleetd-hub.service`
- Machine: `~/.config/systemd/user/fleetd-node.service`

Restart with `systemctl --user restart fleetd-hub` or `fleetd-node`.

## Ports and addresses {#ports}

- The hub listens on port 4790: one port for the app, the machines and MCP clients.
- `fleetd init` picks your Tailscale address when it finds one, otherwise `127.0.0.1` only.
- MCP clients connect to `<hub url>/mcp`.
- Other machines open no port: they connect out to the hub.

Change it with `fleetd init --listen <host:port> --url <url>`.

## Run a second fleet on one machine {#second-fleet}

To try fleetd next to the one you run, give the test fleet its own folder with `FLEETD_HOME` and its own port. Every
command then keeps its files there and never touches `~/.fleetd`.

1. Set up the test hub. Run the `export` in every terminal you use for it.

   ```sh
   export FLEETD_HOME=$HOME/fleetd-test
   fleetd init --no-service --listen 127.0.0.1:4797 --url http://127.0.0.1:4797 \
     --git-identity "Your Name <id+you@users.noreply.github.com>" </dev/null
   ```

2. Start the hub, and keep the terminal open:

   ```sh
   fleetd hub start --listen 127.0.0.1:4797
   ```

3. In another terminal, add this machine to the test hub:

   ```sh
   fleetd pair --worker test-1    # prints a join command with a one-time code
   fleetd node join --hub http://127.0.0.1:4797 --token <code> --machine test-1
   ```

4. Use it as usual:

   ```sh
   fleetd doctor
   fleetd project add ~/src/sandbox --machine test-1 --yes
   ```

Stop both with Ctrl+C. Delete `$FLEETD_HOME` to remove the test fleet. Its services, if any, never touch the first
fleet's. Start the desktop app with the same `FLEETD_HOME` to pair it with the test hub.
