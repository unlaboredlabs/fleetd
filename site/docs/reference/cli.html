CLI reference

Every fleetd command, from fleetd help in the binary this site was built with.

Exit code Means
0 ok
1 failed: a check did not pass
2 usage error
3 refused
4 the hub or the node is unreachable

Commands

Section titled “Commands”

fleetd version

Section titled “fleetd version”

print the fleetd version and protocol

fleetd help

Section titled “fleetd help”

show this message

fleetd update

Section titled “fleetd update”

replace this fleetd with the latest release, then restart its hub and node when nothing runs on them; while something does, they keep the running version until their next restart. --restart-now restarts them anyway

Setting up

Section titled “Setting up”

On the hub machine.

fleetd init

Section titled “fleetd init”

set up fleetd step by step in a terminal: the hub on this machine (home default ~/.fleetd/hub, kept running by a systemd or launchd user service), where it listens (your tailnet when there is one), the claude and gh logins, the machines that run agents, a first project and the desktop app, then fleetd doctor. Run it again to check and repair; it keeps what works. --yes takes every default. Without a terminal and without --yes it only sets up the hub. --url is how devices reach the hub (default http://<listen>); --git-identity is the commit author for every machine (the GitHub noreply address for public repos); --no-service prepares everything but leaves starting the hub to you

fleetd init

Section titled “fleetd init”

make this machine a worker of that hub, without SSH from the hub: the command fleetd pair --worker prints on the hub. Run again, it keeps the node’s enrolment and repairs the rest; --rejoin enrols again with a new code

fleetd doctor

Section titled “fleetd doctor”

run every setup check on the hub now and print each problem with its fix

fleetd uninstall

Section titled “fleetd uninstall”

stop and remove the hub’s service; its data stays unless --purge, which also removes what an older fleetd installed for T3 Code

fleetd machine add

Section titled “fleetd machine add”

set up a machine that runs agents, over SSH (--local: this machine): copies this fleetd there, checks its claude (installed, version >=2.1.300, <2.2.0, logged in), enrolls the node and runs it as a user service, then waits until the machine is online; prints every command first, --dry-run only prints (for a fresh machine, without connecting); --no-service enrolls the node but writes no service and prints how to run it; safe to run again

fleetd machine remove

Section titled “fleetd machine remove”

stop and remove the node’s service on the machine and revoke its key on the hub; --purge also deletes ~/.fleetd/node and ~/.fleetd/claude.env there, and what an older fleetd installed for T3 Code

fleetd pair

Section titled “fleetd pair”

print a one-time code (15 min) that pairs the desktop app with this hub; the app on this machine pairs by itself. The device gets --role (default admin, which changes the hub’s settings) on every machine

fleetd pair

Section titled “fleetd pair”

print the one command that makes another machine a worker of this hub, with a one-time code (15 min): for a machine the hub can’t reach over SSH

Projects

Section titled “Projects”

fleetd project add

Section titled “fleetd project add”

add a project: a checkout on a machine (this one by default), or a GitHub repo cloned onto one (the least busy worker by default), with progress; then its CI, merge rules and what the lead will need. No argument: pick one

fleetd project list

Section titled “fleetd project list”

fleetd project stop

Section titled “fleetd project stop”

stop its lead’s turn and its agents, as you; the lead and its chat stay, and the chat says what stopped

fleetd project remove

Section titled “fleetd project remove”

stop its agents and forget it; its files, branches and worktrees stay

fleetd project set

Section titled “fleetd project set”

fleetd project set

Section titled “fleetd project set”

the most agents the project runs at once (its lead not counted), or the fleet’s cap on running agents (admin key); more wait queued and start as slots free. Lowering stops nothing; --pause-extras has the newest agents above the new max push their work and wait

fleetd project set

Section titled “fleetd project set”

whether the lead may run mechanical tasks on the medium profile (on by default); off runs every task on high

Running by hand

Section titled “Running by hand”

Tip

Run fleetd init --no-service before fleetd hub start: it writes the setup the other commands read. The whole order is in Run a second fleet on one machine.

fleetd hub start

Section titled “fleetd hub start”

run the hub (default home ~/.fleetd/hub, listen 127.0.0.1:4790, writes to an offline machine wait 24 h)

fleetd hub key create

Section titled “fleetd hub key create”

create an agent key for the MCP endpoint; prints the key once, or with --out writes it to a new file (0600) and prints the file’s path

fleetd hub key create

Section titled “fleetd hub key create”

a named agent’s key, to write in a project’s chat (fleetd chat --key-file): its messages show as that agent’s, never yours. Operate on every machine unless --machines. Written to a new file (0600), <hub home>/keys/<name>.key unless --out; prints only the file’s path

fleetd hub key create

Section titled “fleetd hub key create”

a key for a person’s device (the desktop app): what it answers is recorded as the human’s; role defaults to operate on every machine

fleetd hub key list

Section titled “fleetd hub key list”

fleetd hub key revoke

Section titled “fleetd hub key revoke”

takes effect at once, also on a running hub

fleetd node join

Section titled “fleetd node join”

enroll this machine with the hub, then keep its link up (node home default ~/.fleetd/node); --token-file - reads the token from stdin; --enroll-only exits once the hub has accepted this node; sessions use your own claude setup (~/.claude) unless --claude-config-dir names a dedicated one

fleetd node run

Section titled “fleetd node run”

keep the link up for a machine that has joined

fleetd prompts list

Section titled “fleetd prompts list”

every prompt fleetd sends a model, which text is in effect, and “update” where a release changed the default you edited

fleetd prompts show

Section titled “fleetd prompts show”

fleetd prompts show

Section titled “fleetd prompts show”

the text in effect (or the shipped one), or exactly what a session was told

fleetd prompts edit

Section titled “fleetd prompts edit”

edit it in $VISUAL or $EDITOR; warns when a placeholder or a safety rule is gone

fleetd prompts reset

Section titled “fleetd prompts reset”

fleetd prompts diff

Section titled “fleetd prompts diff”

shipped vs yours; after a release changed it, what changed in each

fleetd instructions

Section titled “fleetd instructions”

your custom instructions, appended to every lead and task

fleetd time

Section titled “fleetd time”

where agents’ time went: an order’s critical path, agent time by category, the slowest commands and the findings; a project by id or title (<machine>/<project> when two machines have one), the whole fleet with neither. --since takes 1h to 400d, a date or an ISO time. On the hub machine it needs no --hub or --key-file

fleetd time

Section titled “fleetd time”

keep 1-365 days of timelines (admin key); daily totals are kept 400 days

fleetd metrics

Section titled “fleetd metrics”

what the factory turned out: PRs merged per day by route, time from order to merged, your minutes per merged PR and the share through fleetd, over the last --days calendar days (1-400, today included) in this machine’s zone; one project by id or title (<machine>/<project> when two machines have one), the whole fleet without one. On the hub machine it needs no --hub or --key-file

fleetd metrics

Section titled “fleetd metrics”

keep 30-400 days of landed changes (admin key on every machine)

fleetd status

Section titled “fleetd status”

one row per project, as the app’s Status screen shows it: what it is doing (working, waiting on you, blocked and why, idle), its work in groups (waiting on you, in review, working, landing, idle, done), agents running and the last merge; one project by id or title (<machine>/<project> when two machines have one). --watch prints the rows again after each change; a stale row says so. On the hub machine it needs no --hub or --key-file

fleetd steer

Section titled “fleetd steer”

steer an order’s lead (W41) or one agent (T88) mid-run. Plain: it lands at the agent’s next step, after the tool it is running returns. --now stops that step and delivers at once. --wait follows the receipt: exit 0 acknowledged, 1 not acknowledged, withdrawn or failed. Without --hub it uses the hub on this machine

fleetd steer withdraw

Section titled “fleetd steer withdraw”

take back a steer the agent has not taken in yet

fleetd steers

Section titled “fleetd steers”

an order’s (or one agent’s) recent steers and their receipts

fleetd chat

Section titled “fleetd chat”

write to a project’s lead, as the app does: it starts the lead’s next turn, or lands at its next step while it works; --now (a human key) stops that step and delivers at once. --wait prints the lead’s reply when its turn ends; --follow streams it as it is written. Exit 0 it replied, 1 its turn ended without a reply. A human key writes as you; an agent key as that agent, by its name

fleetd chat history

Section titled “fleetd chat history”

the project’s chat: who wrote each message, when, and what; the newest page, older ones with --page

fleetd work

Section titled “fleetd work”

what is in flight on this checkout’s repo and base: fleetd’s agents, PRs on the merge train, and people’s claims

fleetd work claim

Section titled “fleetd work claim”

check the intent against the work in flight and claim it, with the repo, branch, user.email and changed paths read from this checkout. Exit 0 claimed (or yours: a fleetd agent on its own task’s branch), 1 taken or a likely duplicate (it says by what). Again on the same branch: renews it. --anyway (a human key only) claims taken work regardless

fleetd work done

Section titled “fleetd work done”

end your claim as landed (by default the one on this branch); --landing: the commit on the base. --key-file defaults to $FLEETD_KEY_FILE

fleetd work drop

Section titled “fleetd work drop”

end your claim as dropped (by default the one on this branch): you stop, or leave it to someone else
