Status

Status shows how far along an order, a project or the whole fleet is, and what the work is waiting on.

Status never shows a finish time or an ETA. It shows state instead: what is verified, what is in flight, and what blocks the rest.

Open it

Section titled “Open it”
Where How
Desktop app ⌘. (Ctrl+. on Linux). See The desktop app.
Terminal, the whole fleet fleetd status
Terminal, one project fleetd status storefront
Terminal, one order fleetd status W41
Option Does
--watch Keep it on screen and print each new version as the hub sends it.
--json Print JSON.
--hub <url> --key-file <path> Use a hub on another machine.

See the CLI reference.

What the number means

Section titled “What the number means”

The number is verified work plus credit for work in flight, as a share of the required work.

In the bar Means
█ solid Verified: fleetd checked it.
▒ shaded In flight: partial credit for stages fleetd saw happen.
░ empty Not started.
  • Verified means the item’s PRs were merged by the merge train, and its done-when checks passed. A PR merged by hand doesn’t count. A lead saying “done” moves nothing.
  • In flight credit comes from stages fleetd observed itself: task started, PR open, review passed, CI green, merged.
  • It reaches 100% only when every required item is verified.
  • When it falls, a ↓ line says why: work added, a review blocked, CI failed, or a done item reopened.

Items are must or polish. Polish shows beside the number (“polish 2/5”) and never holds it back.

Size Points
s 1
m 3
l 8

While a lead is still planning, status says so instead of showing 0%. An order with no plan counts as one item until it gets one, and is listed as a risk if it stays without a plan.

Plans and markers

Section titled “Plans and markers”

A project’s plan is milestones of plan items. The lead keeps it with fleetd plan and links work to items with --item P12.

Scope can change, but never silently. After a milestone’s first 10 minutes, adding, dropping or resizing an item needs a reason (--why), and status shows it next to the number:

Items the hub closes itself also get a marker, such as “−2 items: closed with W41, not separately verified”.

What it waits on

Section titled “What it waits on”

“Waiting on” follows the critical path:

  1. The item in progress that the most unfinished work runs through.
  2. What it still waits on, in order: earlier items, then review, CI, merge and done-when checks.
  3. The items it holds up.

An item that has spent over 1.5 times the usual time in its current stage is marked SLOWER THAN USUAL and listed under risks. “Usual” is measured from this project’s own history.

Since you last looked

Section titled “Since you last looked”

Counts what happened in this scope since you last looked: merged PRs, verified items, started orders, failures, new asks and scope changes.

  • The app moves your mark when you leave the view after reading it.
  • fleetd status keeps its own mark on each machine.
  • The two marks never move each other.

Stale data

Section titled “Stale data”

Status never shows old data as live. Each source has a normal rhythm, and the hub flags it stale when it goes quiet:

Source Normally Stale after Status says
A machine a heartbeat every 15 s 45 s of silence “no heartbeat from devbox for 4m”
Claude usage each Claude reply its reset time passes “5h reading from 13:10, before the 14:00 reset”
GitHub every train pass (15 s) 180 s without a good answer “GitHub not reached for 4m: …”
Main CI read every 60 s its period plus 180 s “main CI of acme/storefront unread since 14:05”
A merge train every 15 s 120 s “the acme/storefront train hasn’t run for 3m”

A stale part keeps its last value, with its time and a warning. In the terminal, the first line says “NOT LIVE: 1 stale source”. If the app loses the hub, the view greys out with “Not live: reconnecting”.

To tune when GitHub data counts as stale, see Hub environment.

Faster GitHub updates

Section titled “Faster GitHub updates”

The hub follows GitHub by itself: each train asks about its open PRs every 15 s, and about main’s CI every minute.

To have GitHub tell the hub about changes as they happen:

  1. Set up a public URL that GitHub can reach and that forwards to the hub, such as a reverse proxy. fleetd never creates one.

  2. On the hub, turn on webhooks:

This adds a webhook to every repo the train merges into. Turn it off with fleetd hub github-webhook --off. A webhook only makes the hub look sooner; a lost or forged delivery can’t change what it records.

The headline

Section titled “The headline”

The sentence under the number is written by Claude (haiku, through your claude login on the hub, no tools) from facts fleetd computed.

  • It never mentions time.
  • Every number in it must appear in those facts, or it is thrown away.
  • When it can’t be written, a plain template is shown instead, labelled template.

Change how it’s written with fleetd prompts edit status.headline. See What agents are told.

Daily notification

Section titled “Daily notification”

The app can post a desktop notification at 09:00 and 18:00 with the fleet’s number, its headline and what happened since the last one. Turn it on in Settings → General → Status digest. It is off by default and respects quiet hours.
