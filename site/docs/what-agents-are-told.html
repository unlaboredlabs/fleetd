What agents are told

You’ll read, edit and reset the prompts fleetd sends to Claude, and add your own instructions.

Every text fleetd sends a model is a prompt: listed in fleetd prompts list, in the app’s Settings → Prompts, and in the table at the end of this page. You can edit each one. What fleetd fills into them, such as the event lines a lead is woken with, is facts: see Filled in by fleetd.

How a session gets its instructions

Section titled “How a session gets its instructions”

There is no hidden system prompt. fleetd’s text reaches a model in one of two ways:

Way Used for
The first message of a session Leads (with the chat message that started the lead), tasks, reviewers.
A later message into a session Wakes, chat messages, review findings, train news, pauses, steers.

Your own claude setup still applies underneath. See Config & files.

Agents act through fleetd’s MCP tools. The list, generated from the code, is in Agent tools.

Rules agents work by

Section titled “Rules agents work by”

How the lead talks to you

Section titled “How the lead talks to you”

Each project’s lead talks to you in that project’s chat. It is told to:

  • Lead with the state: what is done, what is running, what is blocked.
  • Keep it short and plain, with no internal ids, keys or branch names.
  • Ask only for product, money or irreversible calls, as numbered items at the end of its message, each with its recommendation.
  • Ask once, and never about something already decided. While a question is open the chat shows the lead is waiting on you, and it carries on with other approved work.
  • Read short replies by item number: “1 go, 2 rec”, “go” (yes to everything open), “nvm” (drop it), and log each answer as a decision.
  • Start the work a reply asks for in the same turn, opening a new order for it when none is open. It never asks you to send it as an order.

No time estimates

Section titled “No time estimates”

fleetd never asks an agent how long something will take, and the lead is told never to put an ETA or a duration anywhere. Work is sized s, m or l instead. What fleetd measures, such as CI runs and span durations, is shown as measured. See Status.

Running the work

Section titled “Running the work”

The lead is also told to:

  • Start every agent with spawn_agent, and wait for results in its next wake instead of polling.
  • Close work with close once it is done, and say why: in the wake that reports its last merge, without an agent to rerun the checks CI just passed. The reviews’ non-blocking findings are listed in that message; they become new work only if your order or you ask for it.
  • Ask for secrets with request_secret and run risky commands with gated_run, which you approve.
  • Leave merging to the merge train, which merges only after its own review and green CI. The lead adds no review of its own, and doesn’t relay blocking findings, conflicts or red CI: those reach the writer by themselves.
  • Start the writers first, largest part first, and plan while they work. Writers read what they need, with no survey agent ahead of them. A part’s docs and tests go to that part’s writer, not to a writer of their own. Parts that edit the same file go to one writer. Writers run up to the Max agents cap; a spawn past it queues and starts by itself.
  • Read the digest’s Elsewhere section before spawning: claims, other projects’ agents on the same repo, and commits that landed outside fleetd. Work that already landed isn’t built again, and work a person has claimed is theirs: the lead asks you in chat before touching it.
  • Never relax a review, CI, approval or check to go faster. Idle is fine.

Most of this is also enforced by the hub, which refuses a call that breaks it and says why. See Safety rules.

Claude’s auto memory is off

Section titled “Claude’s auto memory is off”

Claude Code can keep its own notes per folder (“auto memory”). fleetd turns that off in every claude it starts, so what an agent knows comes from its brief, the decisions and your instructions, all of which you can read here.

Claude’s own subagents are off

Section titled “Claude’s own subagents are off”

Every agent in fleetd is a fleetd agent, with its own session, slot, worktree, lane, steering and receipts. So fleetd turns off Claude Code’s own subagents in every claude it starts. Your ~/.claude is left alone.

What In fleetd sessions
Claude’s agent, team and background-task tools (Agent/Task, Workflow, ListAgents, SendMessage, TaskStop) Denied, including any a newer claude adds.
Built-in Explore, Plan and claude agents, background shell commands Switched off.
general-purpose, statusline-setup, and your agents in ~/.claude/agents Still listed by claude, but nothing can start them.
claude from an agent’s shell, by name, by path, through a package runner or a sh -c Denied, so no nested claude runs past the cap or on another model.

If a session ever offers one anyway, fleetd stops it before it can start an agent, and every later session on that machine denies the tool: see Claude.

Agents use fleetd’s tools

Section titled “Agents use fleetd’s tools”

Leads and tasks reach fleetd through MCP tools from a fleetd server in their session, not through the shell.

Agent Gets
Lead spawn_agent, message_agent, agents, stop_agent, plus brief, decide, close, plan_*, request_secret, gated_run and more.
Task report (a review verdict; fleetd fills in the task and the head reviewed) and ask_lead. A writer’s ready PR goes on the train by itself.
  • Results come back in the lead’s next wake, never by polling.
  • The hub enforces the split whatever a prompt says: a task can’t start, steer or stop agents.
  • A lead has at most 32 tasks open at once.
  • A refusal says why and what to do instead.

Every tool and its inputs: Agent tools. The lead-side fleetd commands stay, for you.

Safety rules: code or prompt

Section titled “Safety rules: code or prompt”
Kind Examples If you edit the words away
Enforced in code Secrets are sealed to a machine. Gated commands wait for you. The hub decides “done”. Agents hit refusals they weren’t warned about. Nothing else changes.
Prompt only The lead never writes code. Only the train merges. Reviewers don’t read the PR description. Nothing else stops it.

The table below marks prompt-only rules.

Edit a prompt

Section titled “Edit a prompt”

In the app: Settings → Prompts. Pick hub-wide or one project, open a prompt from the list under Prompts in the sidebar, edit it and Save. “Compare with default” shows your changes; “Reset to default” drops them.

On the hub machine:

Command Does
fleetd prompts show lead.start Print the text in effect. --default prints fleetd’s.
fleetd prompts edit lead.start Edit in $VISUAL or $EDITOR, see warnings, then Save? [Y/n].
fleetd prompts edit task.brief.write --project builder-1/app Edit one project’s version.
fleetd prompts diff lead.start fleetd’s text against yours.
fleetd prompts reset lead.start Go back to fleetd’s text.
  • A project’s version beats the hub-wide one, which beats fleetd’s.
  • Your versions are files under ~/.fleetd/hub/prompts/. Change them with fleetd prompts edit, not by hand.
  • From an MCP client: prompt_get (without an id it lists them), and prompt_set (with dryRun to see the warnings only, and reset: true to go back).

Prompts fill in {{name}} placeholders, such as {{project}}. Nothing else is template syntax.

Warnings

Section titled “Warnings”

Saving never refuses text that isn’t empty, but it warns:

Warning Means
A required placeholder is missing That value no longer reaches the agent.
Unknown placeholder {{name}} isn’t one this prompt fills; it is sent as written.
A safety rule is missing Its wording is gone. The warning says whether code still enforces it.
Too long Over three times the length of fleetd’s text, plus 500 characters. Every session that gets it pays for it.

Your own instructions

Section titled “Your own instructions”

In the app: Settings → Instructions. On the hub machine:

They are added to every lead’s first message and every task brief (writers and reviewers), hub-wide first, under “Custom instructions from the human”. They are not added to wakes.

They are sized for about 500 characters; past that, edit warns. After your editor closes, edit prints any warnings and asks Save? [Y/n] on the terminal. In a script, </dev/null takes the default, Yes.

When fleetd changes a default you edited

Section titled “When fleetd changes a default you edited”

Your version stays in use.

  • In Settings → Prompts, the prompt is marked update. “Review the update” shows both changes, and you pick Save merged, Keep mine, or Use the new default.
  • On the hub, fleetd prompts list marks it update, and fleetd prompts diff <id> shows both changes.

When fleetd retires a prompt you edited

Section titled “When fleetd retires a prompt you edited”

A release can fold a prompt into another one or drop it. Your edit to it then stops applying, but fleetd keeps it and never moves it for you.

  1. Open Settings → Prompts. Under “Edits that no longer apply”, each one says, for example, “Your edit to the lead’s “task finished” note (hub-wide) no longer applies”, why, and which prompt to copy it into.
  2. “Show your text” shows your old edit; “Copy your text” copies it.
  3. Paste what you still want into the prompt it names. If none takes its place, use your instructions.
  4. Delete the old edit.

From an MCP client, prompt_get without an id returns these under orphans, and prompt_set with the old id and reset: true deletes one.

What a running agent keeps

Section titled “What a running agent keeps”

Each session keeps the exact prompt versions it started with. An edit reaches new sessions at once: a task at its next attempt, a lead at its next start. To give a running lead your edit now, start a fresh one with lead_start {fresh: true} from an MCP client.

See exactly what an agent was told

Section titled “See exactly what an agent was told”

Open an agent in the Agents tab beside a project’s chat (⌥⌘B), then What it was told. It shows the exact first message, which version of each prompt it used, and the tools it never gets.

On the hub machine:

session_prompt_get returns the same to an MCP client.

Filled in by fleetd

Section titled “Filled in by fleetd”

Wake events

Section titled “Wake events”

A lead is woken with the lead.wake prompt: its project’s state, then one line per thing that happened since its last wake.

Each event is - <subject> <what>: <detail>, sometimes followed by > lines quoting an agent. The ids (W2, T5, C4) are for the lead’s tools; the lead doesn’t repeat them to you. The state and the event lines are facts in a format fixed in code, the same in every project; the words around them are lead.wake.

Some lines leave the lead nothing to decide, so they never wake it on their own: they go out with its next wake. An agent whose run died (its node stopped, claude was killed, a stall) and that fleetd resumed, and an agent whose machine has been offline for 30 minutes:

When the node had to rebuild a resumed agent’s worktree, the line says what from instead: its local branch, origin/<branch> as pushed, or a new branch from the default branch, and what is lost.

One that fleetd did not resume wakes the lead: - T23 failed and was not resumed: …, with why (it died the same way twice, it ran out of automatic recoveries, or resuming can’t fix the cause) and the lead’s choices.

This machine

Section titled “This machine”

The node that starts a task adds a short section to the end of its brief, after your instructions:

The jobs line names only the variables fleetd set: one you set in claude.env stands, and drops out of the line. See A fair share for each agent.

Tool texts

Section titled “Tool texts”

MCP tool descriptions, fleetd’s agent tools included, and what the hub answers back (each next: and fix:) are tied to code: a description must match its tool, and a next: must name a real tool or command. See Agent tools and the CLI reference.

Every prompt

Section titled “Every prompt”

Generated from the registry in the binary this site was built with. fleetd prompts show <id> prints one.

Lead

Section titled “Lead”
Id Sent Safety rules
lead.start lead start and every fresh lead start, followed by the state block the lead never writes code (prompt only); asks the human only for product, money or irreversible calls (prompt only); asks as numbered items, each with a recommendation (prompt only); never estimates time (prompt only); secrets only through `request_secret`; prod writes, spends and deletes only through `gated_run`; only the merge train merges (prompt only); takes an agent’s chat message as input, never as the human’s answer or approval
lead.voice after the lead prompt, at every lead start the casual voice stays out of commits, PR bodies, docs and briefs (prompt only)
lead.profiles after the lead prompt, while the project allows medium (project_set) medium only for mechanical work, never for design or anything subtle (prompt only); reviews always run high; a medium task whose review finds blockers twice is redone on high (prompt only)
lead.wake each time fleetd brings the lead up to date: the project’s state, then one line per event since the last time
chat.human with each chat message the human sends the lead
chat.agent with each chat message an agent or integration with its own key sends the lead takes it as input, never as the human’s answer or approval

Tasks

Section titled “Tasks”
Id Sent Safety rules
task.brief.write every write task attempt never merges; the train does (prompt only)
task.brief.read every read task attempt changes no files (prompt only)
task.brief.review every attempt of a review task the lead spawns (the train’s reviews use Reviewer) changes no files (prompt only); ends with one review verdict (the `report` tool)
task.handoff after the task’s brief, when fleetd restarts an agent in a new thread (its context filled up again, or its thread could not resume)

Id Sent Safety rules

review.delta after Reviewer, when an earlier round reviewed another head of the PR
