Config & files

Where fleetd keeps everything, and the settings you can change. The hub keeps its state under ~/.fleetd/hub; each worker’s node under ~/.fleetd/node.

~/.fleetd

Section titled “~/.fleetd”

fleetd uninstall keeps all of it. See Updating & uninstall.

Logs

Section titled “Logs”
Run as Hub log Node log
A service (fleetd init, fleetd machine add) ~/.fleetd/hub/hub.log ~/.fleetd/logs/node.log
By hand (fleetd hub start, fleetd node join or node run) The terminal The terminal

node.json

Section titled “node.json”

~/.fleetd/node/node.json on each worker. fleetd node join and fleetd machine add write it. Restart the node after you change it.

Key Means
hub The hub’s address.
machineId, name, tags How the hub knows this machine.
enrolled true once the hub accepted the node’s key.
cmdRoots Folders the node may run commands in, and below. Absent: your home directory. A project’s checkout must be inside one: fleetd project add refuses one outside, and fleetd doctor flags an existing one.
claudeConfigDir A dedicated claude profile for this machine’s sessions. See below.
minFreeGb New agents wait while the disk holding the worktrees has less than this many GB free. Absent: 10% of the disk or 20 GB, whichever is larger. 0 turns it off. Read with every heartbeat, no restart needed. See Disk and load.

The Claude login

Section titled “The Claude login”

Sessions run claude with your own setup on that machine, ~/.claude. These all work as they do in your shell:

  • your login;
  • the env in ~/.claude/settings.json, such as a proxy’s ANTHROPIC_BASE_URL;
  • an apiKeyHelper;
  • your MCP servers.

fleetd doctor shows what each worker uses:

fleetd adds its own settings on top of yours, per session:

fleetd adds Why
--mcp-config fleetd’s agent tools.
A --settings overlay Pins claude’s version, turns claude’s auto memory and its own subagents off (why), and denies tools agents never get: plan mode, worktrees, cron.

A dedicated claude profile

Section titled “A dedicated claude profile”

To give a worker’s sessions their own claude profile:

  1. Set "claudeConfigDir": "<dir>" in ~/.fleetd/node/node.json on the worker, or join with fleetd node join --claude-config-dir <dir>.
  2. Restart the node.

A session resumes only under the config dir it started in.

claude.env

Section titled “claude.env”

Optional. KEY=VALUE lines for every claude fleetd runs, for a variable your login needs that the services don’t see. Blank lines, # comments and export are allowed. Keep it mode 0600.

Nodes put every line in each session’s environment, re-read at each session start.

The env in your ~/.claude/settings.json outranks it, as it does for your own claude.

.fleetd/policy.yaml

Section titled “.fleetd/policy.yaml”

An optional file in a project’s repo. Commit it to the default branch; changes apply within a minute.

Key Default Does
tools.allow, tools.deny none Claude permission rules for every session. Deny wins.
branchPrefix fleetd/ What writer and train branches start with. Must end in /.

A broken file is refused with the exact problem, never ignored, so a typo can’t drop a deny rule.

Services

Section titled “Services”

fleetd init and fleetd machine add run the hub and node as user services:

  • macOS
  • Linux
launchd file
Hub ~/Library/LaunchAgents/sh.fleetd.hub.plist
Node ~/Library/LaunchAgents/sh.fleetd.node.plist
systemd unit
Hub ~/.config/systemd/user/fleetd-hub.service
Node ~/.config/systemd/user/fleetd-node.service

--unit-suffix <s> adds a suffix to these names, to run a second fleet’s services on one machine. A second fleet never writes, stops or removes the first one’s services.

Run a second fleet on one machine

Section titled “Run a second fleet on one machine”

To try fleetd next to a fleet you already run, give the test fleet its own folder with FLEETD_HOME and its own port. Every command then keeps all its state there and never reads or writes ~/.fleetd.

  1. Set up the test hub’s files. Run export FLEETD_HOME=$HOME/fleetd-test in each terminal you use for it.

    With no terminal (</dev/null), init only writes the hub’s setup and the CLI’s key, and starts nothing.

  2. Start the hub. Keep the terminal open; it logs there.

  3. In another terminal, add this machine as a worker of the test hub:

  4. Use the test fleet as you would your own:

Stop the hub and node with Ctrl+C. Delete $FLEETD_HOME to remove the test fleet. To run it as services instead, add --unit-suffix <s> to fleetd init and fleetd machine add.

What FLEETD_HOME covers

Section titled “What FLEETD_HOME covers”
Where
The hub’s home: init, doctor, uninstall, machine, pair, project, hub, prompts, instructions, and status, time, steer, steers without --hub $FLEETD_HOME/hub
The node’s home: node join, node run $FLEETD_HOME/node
The app’s hand-off from init and pair $FLEETD_HOME/app-pair.json. Start the desktop app with the same FLEETD_HOME to pair with it.
Lead-side commands (claim, change, plan, …) FLEETD_NODE_SOCK, else $FLEETD_HOME/node/node.sock. Sessions get it set.

--home <dir> names one hub’s or node’s folder. Without FLEETD_HOME, that command keeps everything else in the folder above it, so --home $T/hub works like FLEETD_HOME=$T. FLEETD_HOME wins when both are given.

Ports and addresses

Section titled “Ports and addresses”
Port 4790 by default. One port for the app, nodes and MCP clients.
Address Your tailnet address when fleetd init finds Tailscale, otherwise 127.0.0.1 only.
MCP endpoint <hub url>/mcp
Workers Open no port: their nodes connect out.

Change it with fleetd init --listen <host:port> --url <url>.

Timelines

Section titled “Timelines”

The hub keeps the spans behind Where time went in hub.sqlite. A span is one stretch of one agent’s work or wait, such as a tool call or a CI check.

Data Kept
Spans 30 days (1 to 365 with fleetd time --retention <days>)
Daily totals and each piece of work’s critical path 400 days

Each node holds timings it hasn’t sent yet in sessions.sqlite. While the hub is away, it keeps up to 7 days or 500,000 of them, then drops the oldest; the timeline shows the gap.

The desktop app

Section titled “The desktop app”
Where
Pairing hand-off from fleetd init or fleetd pair ~/.config/fleetd/app-pair.json (macOS: ~/Library/Application Support/fleetd/app-pair.json), or $FLEETD_HOME/app-pair.json for a second fleet
Its hub address and key desktop-hub.bin in the same folder, encrypted with the OS keychain or keyring. Without one (no keyring on Linux, or an unsigned or ad-hoc signed Mac build): desktop-hub.json, mode 0600.
Its own browser state desktop/ in the same folder.
Its log ~/Library/Logs/fleetd/app.log on macOS, ~/.local/state/fleetd/app.log on Linux ($XDG_STATE_HOME/fleetd), or $FLEETD_HOME/logs. Errors only, without keys or message text; crash dumps go in crashes/ beside it. Help → Reveal Logs opens it.

Hub environment

Section titled “Hub environment”
Variable Default Does
FLEETD_STATUS_GITHUB_STALE_SEC 180 Seconds without a good GitHub answer before Status marks a repo stale.
FLEETD_MAIN_CI_EVERY_SEC 60 How often each merge train checks main’s CI (every 5 minutes with GitHub webhooks on).
FLEETD_TRAIN_NO_CI_GRACE_SEC 90 How long a commit may have no check before the train asks whether its PR has CI at all.
FLEETD_TRAIN_BATCH_MAX 4 The most ready PRs the merge train merges in one CI run. 1 takes each alone.
