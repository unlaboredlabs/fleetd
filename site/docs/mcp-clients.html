Writing to a lead

With a human key, chat_send writes as you. Any other key writes as an agent, by the key’s name: the lead takes it as input, never as your answer or approval. Don’t give Claude Code a human key: it could then speak and approve as you.

claude mcp add writes to your Claude config. --scope picks where:

Scope Where it applies Note
local (default) This folder, only for you.
project Everyone who opens this repo: written to .mcp.json. Don’t use with a key in --header: you’d commit the key.
user All your folders.

Claim work before you start it

Section titled “Claim work before you start it”

fleetd keeps one ledger of the work in flight on each repo: its agents, the PRs on its merge train, and what people claimed from their own sessions. A session that checks it first doesn’t build what an agent is already building.

Claude Code needs nothing more than the connection above. The hub’s MCP instructions, which Claude Code adds to every session’s system prompt, tell it to call work_claim before a code change and work_done when the change lands or is dropped, and to tell you when the work is taken. A session might go like this:

Tool Does Role
work_claim {repo | projectRef, title, base?, branch?, keys?, paths?, changed?, authorEmail?, notDuplicateOf?, notDuplicateWhy?, anyway?} Checks the intent against the work in flight on the repo’s base and claims it in one call. status is claimed; renewed (your claim on the same branch, updated); taken (someone else has the same issue, PR, branch or plan item); possible_duplicate (most of the same words, or the same words and files), or yours (fleetd’s own agent on its task’s branch: the task already holds it). Keys and paths a renewal adds are checked like a new claim’s. For a likely duplicate, call again with notDuplicateOf and notDuplicateWhy if it’s different work. With a taken item, anyway: true claims it regardless, but only with a human key: any other key may be one of fleetd’s own agents. operate
work_list {repo | projectRef, base?, paths?} What is in flight on the repo’s base, newest first, with each item’s keys and files (paths: false leaves out what each writer has changed so far, which asks its machine). Expired claims come last. recentLandings lists what reached the base outside the merge train in the last 24 h, and how. read
work_done {claimId, outcome, landing?, reason?} Ends your claim: landed (with its commit) or dropped. A human key can end anyone’s. operate

repo is the origin remote in any form, on any host: git@github.com:acme/shop.git, https://gitlab.example.com/g/shop, /srv/git/shop.git. With no base, the base is the project’s (or that of a project on the repo), else main. A claim lasts 12 hours after your last work_claim on it, then shows as expired for a day. Matches only list it once it has expired. When no project is known to be on the repo yet, the hub first reads the remotes of your projects that it hasn’t matched to a repo, waiting a few seconds. If none matches, the answer’s warning says the agents’ work may be missing from it.

Roles

Section titled “Roles”
Role Can
read Read chats, status, time and prompts.
operate Also write to leads, set a project’s max agents, and manage projects.
admin Also change hub settings, such as timeline retention.

--machines '*' gives the role on every machine; --machines devbox,laptop limits it to those.

Command Does
fleetd hub key list Lists keys.
fleetd hub key revoke <keyId> Ends a key at once, also on a running hub.

A human key (fleetd hub key create --human) is for a person’s device. Some tools, such as stopping a project, answering an approval or entering a secret, need one.

Tools for the chat

Section titled “Tools for the chat”
Tool Does Role
chat_send {projectRef, text, attachments?, clientRequestId} Write to a project’s lead. It starts a turn when the lead is idle, steers it when it works, or waits while it starts. The lead reads it as your words with a human key, as an agent’s with any other. operate
chat_history {projectRef, before?, after?, limit?} A page of a project’s chat, oldest first; up to 100 messages. Without before or after, the newest. read
approval_answer {requestId, decision, message?} Approve or deny an approval item: decision is approve or deny; message is a denial’s reason for the lead. operate, human key
secret_submit {requestId, sealed} Answer a secret item with a value sealed to the target machine. operate, human key
decisions_list {projectRef, limit?} Every decision in the project, project-wide or for one order, newest first: in force, replaced by a newer one, or revoked (by whom, when, why). orders names each order by its title. read
decisions_overturn {decisionId, value?, why} Take back a decision in force. Without value it is revoked and the lead asks again when it comes up; with value a new decision on the same question replaces it, as yours. The lead reads the change, and your why, at its next wake. operate, human key
requests_list {projectRef?, state?} Secret and approval requests, newest first, with their state. A secret’s value is never in it, only its fingerprint. read
project_stop {projectRef, reason?} Stop every running and queued agent of the project and tell the lead in its chat. Merged PRs, the lead and the chat stay. operate, human key
attachment_put {name, mime, dataB64, uploadId?} Upload a file (image, text or PDF, at most 25 MiB) for a message; up to 20 go with one message. operate
attachment_part {dataB64, uploadId?, offset?} One piece of a file too large for one request, in order: pass the uploadId it returns and the bytes sent so far as offset with the next piece, and the last piece to attachment_put with the uploadId. operate
attachment_get {projectRef, attachmentId} Read a file attached to a project’s chat. read
project_files {machineId, projectId, query} A project’s files, for @-mentions. read
status_get One row per project: its state word, its work in groups, agents running and the last merge. read
agents_list {projectRef?, endedSince?} Every agent of your projects: its role, task, what it’s doing now, when it started and its PR. read
agent_work {machineId, threadId, before?, limit?} A page of one agent’s recent messages, commands and edits, oldest first. Secrets show as [secret]. read
pr_list {projectRef, closedSince?, cursor?}, pr_get {repo, number} A project’s PRs, up to 60 a page (nextCursor, passed as cursor, reads the next), and one in detail: description, checks, reviews with their findings, its place in the merge queue and the agent that wrote it. read
pr_files {repo, number, offset?}, pr_diff {repo, number, path, offset?} A PR’s changed files, and one file’s diff a page at a time. read
events_list {projectRef, before?, types?, hubWide?, limit?} A project’s events, newest first, back through the last 30 days: agents started and finished, reviews, merges, requests. hubWide adds the hub’s own, such as a device paired. read
workstream_list, order_get, thread_tail, fleetd_status Lower-level views of the lead’s work. read

projectRef is {"machineId": "devbox", "projectId": "<id>"}; fleetd project list prints both, as <machineId>/<projectId>.

clientRequestId is any unique string you choose per request. Sending the same one again returns the same message instead of a second one. events_wait waits for changes, so a client doesn’t need to poll: a new message is a chat.message event.

Tools for projects: project_discover, project_add {path | url} (a path is a git checkout or a plain folder; with dryRun to see its CI and merge rules, and where a clone would go, without adding it) and project_remove. Tools for Navis: navi_create, navi_list, navi_rename and navi_archive. A clone answers with an addId, then sends project.clone_progress events, then project.added or project.add_failed.
