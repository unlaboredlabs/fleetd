Projects

You’ll add a repo as a project, send it work, and follow that work to merged pull requests.

What you can pass

Section titled “What you can pass”
You pass fleetd does
A GitHub URL or owner/repo Clones it onto the least busy online worker, into ~/src (or ~/code, ~/projects).
A path, such as ~/src/storefront Adds that existing checkout on this machine.
Nothing, in a terminal Lists checkouts on every worker and your repos from gh repo list, to pick from.
Option Does
--machine <id> Clone to, or look for the path on, that worker.
--dest <dir> Clone into that folder.
--use-existing Add the folder’s checkout when it already holds the same repo. Without a terminal, this is how you accept it.

Checkouts must be under your home directory

A node runs commands only under its cmdRoots, which default to your home directory. fleetd project add refuses a checkout elsewhere, such as in /tmp, and says how to fix it: list its folder in cmdRoots in node.json and restart the node. A new --dest folder counts where it will be.

fleetd reads GitHub through gh on the hub machine. A private repo clones on any worker where gh auth login was run. When something is in the way, such as an offline worker or a folder that exists, it prints the command that fixes it.

List and remove projects

Section titled “List and remove projects”

list prints each project as <machineId>/<projectId>, its title and its folder. remove stops the project’s agents and forgets it. Its files, branches and worktrees stay.

Which branch fleetd works on

Section titled “Which branch fleetd works on”
What Is
The base each writer branches from The checkout’s origin/HEAD, else its current branch.
A task’s branch fleetd/T<n>-<slug>, such as fleetd/T1-fix-readme-typo. Change the fleetd/ prefix with branchPrefix in the policy file.

Its lead

Section titled “Its lead”

Each project has one lead and one chat with it. Your first message starts the lead: there is nothing to start by hand. See Chat with the lead.

If the lead can’t start, your message waits and the chat says why. Common causes:

Cause Fix, on the worker
claude is logged out claude auth login
claude is outside the supported versions See claude versions
The worker is offline See Machines

Once the worker is back with a working claude, the lead starts and reads every waiting message.

Max agents

Section titled “Max agents”

Each project has a cap on how many agents run at once, and the fleet has one across all projects. The hub enforces both; the lead plans to them.

Cap Counts Default Set it
Per project: Max agents The project’s agents: writers, readers, reviewers, verifiers. Not the lead. The fleet cap Click “agents 6 / 12” in the project’s chat header, or use Settings → Agents. From 1 up to the fleet cap.
Fleet-wide Every project’s agents together. Not the leads. Settings → Agents → Whole fleet. Needs an admin key.

The header shows “· 2 waiting” when agents are queued. Before you save, the slider says what the change will do.

Writers in a project run side by side, each in its own worktree and branch. The lead gives them slices that touch separate files; if two PRs still conflict, the merge train sends the later one back to its writer.

From a terminal:

From an MCP client: cap_set {project: {projectRef, maxAgents, pauseExtras?}} with an operate key, or cap_set {cap} for the fleet cap with an admin key.

When the cap is reached:

  • A new agent queues; it doesn’t fail. The lead is told its place in line, and the hub starts it the moment a slot frees.
  • New agents also wait while their machine is short of disk or CPU (Disk and load).
  • Reviewers and verifiers count toward the cap, but a review that gates a merge goes first, so a low cap never stalls the merge train.

Changing it while work runs:

You What happens The line in the chat
Lower the cap Running agents finish their current work; new ones wait. Nothing is killed. Max agents 6 → 3: 6 running finish their work; new agents wait.
Lower it and tick “Pause the 3 extras now” (“Pause the extra one now” for one) Agents over the cap push their work in progress and wait. Each resumes when a slot frees. Max agents 6 → 3: 3 agents push their work and wait; 3 keep running.
Raise the cap Queued agents start at once, and the lead is told how many slots are free. Max agents 3 → 6: 2 queued agents start now, 1 slot free.

The lead plans to the cap: at most that many slices at once, the rest queued by value, each slot filled as it frees. It never works around the cap: it doesn’t do a writer’s work itself, or ask you to raise it unless you asked about speed. At a cap of 1 it works one piece at a time and says so once.

Models and cost

Section titled “Models and cost”

Every agent runs on claude-opus-5-5, with one of two profiles:

Profile Effort Runs
high high The default. The lead, every review, every helper call, and every task the lead doesn’t mark medium.
medium medium Mechanical tasks the lead picks: dead-code deletions, renames, test removals, doc fixes, moving files, plain wiring, screenshot recaptures. Never design, concurrency, auth or secrets, approvals or the merge train.

The lead picks the profile for each task it starts. A medium task whose review finds blockers twice is redone on high. Each agent’s profile shows on its lane, in fleetd task status and in fleetd status (T12 medium), and the time view splits agent time and output tokens by profile, so you can see what medium saves.

To change Do
Whether the lead may use medium fleetd project set <machine>/<project> --medium off runs every new task on high; --medium on allows medium again (the default).
When the lead picks medium Edit the Task profiles prompt (lead.profiles) like any prompt. It takes effect at the lead’s next start.

There is no other model or effort: no setting, flag or policy key picks one. An older policy file’s defaults.model and defaults.effort are ignored.

How the lead schedules work

Section titled “How the lead schedules work”

The lead plans each piece of work as small items, sized S, M or L, some waiting after others. It starts every item it can in parallel. Spawns past the cap queue and start by themselves as slots free, and the lead is woken whenever an agent finishes or a PR merges. fleetd never starts work of its own.

Slices are reviewed as they land: a writer reports each finished PR (report, kind slice_ready), or marks its draft PR ready on GitHub. fleetd puts it on the train and starts its reviewers right away, while the writer goes on. A new commit is reviewed again from what changed.

No gate relaxes. Every PR still gets its tier’s reviews and green CI and goes through the train, done is still decided by the done-when checks, and anything that needs your approval still waits for it. The reviewers fleetd starts count against the slots and the lead’s limit of 32 open tasks like any task.
