# fleetd on Bun (experiment)

A TypeScript fleetd (hub, node, CLI) beside the Rust one, speaking the same wire protocol and opening the same
database, so the apps and the lab run unchanged against either (D342, D343). TypeScript runs directly on Bun; the
release form is one file from `bun build --compile`; type checking is tsc-rs, a Rust port of tsc 7. The Rust code is
untouched and stays the product.

```sh
cd experimental/bun
bun install                # tsc-rs and Bun's types, pinned in bun.lock
bun run gen                # regenerate src/gen/ and PORT_MAP.md from the Rust tree and the PORTED files
bun run progress           # the PORTED files' ticks, counted per area
bun run typecheck          # tsc-rs -p tsconfig.json
bun test
bun run compile            # dist/fleetd, one binary: fleetd hub start, fleetd node …, every other command
bun run smoke              # the binary end to end: version, hub start on a fresh home, /healthz, SIGTERM
bun run check              # all of the above, as CI's `bun (experimental)` job runs them
bun src/main.ts hub start --home "$TMPDIR/hub" --listen 127.0.0.1:4795   # from source
```

Never point it at the live hub's home or database: tests and runs use a fresh `--home` under `$TMPDIR`, and set
`FLEETD_HOME` too, so nothing reads `~/.fleetd`.

## Layout

`src/` mirrors `crates/fleetd/src/`: the Rust module `hub/train` is ported in `src/hub/train/`, `node/sessions` in
`src/node/sessions/`, `cli/project.rs` in `src/cli/project.ts`. [PORT_MAP.md](PORT_MAP.md) lists everything there is to
port, by area, with its module; each area's writer owns its modules' directories.

| Path | What |
|---|---|
| `src/main.ts` | the binary's entry: `src/cli/index.ts` dispatches `hub start`, `node …` and the rest |
| `src/shared/contracts.ts` | the wire types, re-exported from the desktop app's generated `contracts.ts` (crates/fleetd-contracts renders it); never copy a type by hand |
| `src/shared/errors.ts` | `ToolError` (the contracts' `{ code, message, fix }`) and `NotImplemented` |
| `src/hub/store/` | `HubDb` over bun:sqlite: the Rust tree's migrations run in order (same runner, same `migrations_applied` hashes), WAL, and `db.read()` on a worker thread for long reads |
| `src/hub/auth/` | key checking (`fld_` keys by SHA-256, revocation on the next call) and the HTTP bearer check |
| `src/hub/api/` | `Hub` (the shared context; areas keep their services with `hub.area(name, make)`), the tool `Registry`, grant checks |
| `src/hub/http/` | `Bun.serve` with the Rust router's routes; websockets pick their handler when they upgrade (`route.ts`) |
| `src/hub/serve/` | `fleetd hub start`: flags, build, serve, loops, stop on SIGTERM |
| `src/gen/` | generated by `scripts/gen.ts`; don't edit |

## How a module plugs in

- **Tools.** Every MCP tool in the contracts' table is registered as a stub that answers `failed` with "not ported to
  Bun yet: src/hub/<module>". A module replaces its own in `src/hub/<module>/tools.ts`:
  `export function register(tools: Registry) { tools.add("project_get", async (hub, caller, input) => …) }`. Input and
  output are typed from the contracts' `ToolMap`; the registry checks the tool's role first. Throw a `ToolError` to
  refuse. `src/gen/areas.ts` calls every module's `register`, so no one edits a shared list.
- **Lead calls.** A module answers the lead calls its Rust `calls.rs` registers, in `src/hub/<module>/calls.ts`:
  `leadCalls(hub).register("task_spawn", (caller, call) => …)` from its `loops.ts` `start(hub)` (src/hub/lead_calls).
  The call arrives decoded against its contract (crates/fleetd-contracts/schema/LeadCall.json, rendered by
  `fleetd-schema` and kept out of the app's contracts.ts): types, brand patterns and bounds checked, defaults filled,
  unnamed fields dropped, and lead_calls.rs's `checked!` rules run; other structs' `checked!` rules stay the handler's.
  `caller` is `{ projectRef, by, agent, threadId? }`, already attributed and through the policy; return the result
  without its `op` (the dispatch adds it), or throw a `ToolError` to refuse. The link answers each `lead_call` frame
  with `onLeadCallFrame(hub, machineId, frame, send)`.
- **Loops.** `src/hub/<module>/loops.ts` `start(hub)` starts the module's background loops (the Rust hub's
  `start_loops`); stop them on `hub.shutdown.signal`.
- **Routes.** Each HTTP route is a stub in its module (`src/hub/pair/http.ts`, `src/hub/app_ws/socket.ts`, …) that
  throws `NotImplemented` (answered 501). A websocket route calls `upgrade(req, ctx, handler, state)`.
- **The database.** `hub.db.conn` is the bun:sqlite `Database` (opened `strict`: named parameters bind without their
  `$`); `hub.db.transaction(fn)` is `BEGIN IMMEDIATE`; `await hub.db.read(sql, params)` for a read that can take long.
  The schema is the Rust tree's migrations: a new table is a Rust migration first.
- **The node link.** Its types are Rust-only (crates/fleetd-contracts/src/node_link.rs is not rendered to TypeScript);
  `src/gen/wire.ts` has its tags, session call ops, lead call ops and agent-mcp's tools, generated from the Rust source.
- **Native pieces.** Only where the research said so: a session's PTY stays with the Rust binary's
  `fleetd session-host`, and the screen helper's JPEG work with its Rust helper; the Bun node starts those binaries.
  The session host ships beside the Bun build as `fleetd-session-host` (`bun run helper` copies a Rust build into
  `dist/`; `FLEETD_NATIVE_BIN` names another); a node without one shows as degraded, and starts no session.
- **PORT_MAP.md.** Generated: never edit it. Tick an item when its module does it and a test covers it by adding
  the item's key (the `<!-- … -->` id on its PORT_MAP.md line, without the comment marks) as a line of its module's
  `src/<module>/PORTED`, e.g. `src/hub/app_ws/PORTED`. Create the file if it isn't there; for a module that is one
  file, such as `src/cli/project.ts`, it goes in a directory of that name (`src/cli/project/PORTED`). Then run
  `bun run gen`, which sorts the file, and commit both. Each module ticks in its own file, so parallel PRs don't
  conflict, and the merge train regenerates PORT_MAP.md itself on a conflict. A `- [x]` left in PORT_MAP.md by a
  branch from before PORTED still counts, and moves into its module's PORTED when you run `bun run gen`, so to untick
  an item, remove its key from PORTED and its `x` from PORT_MAP.md. `bun run progress` prints the counts per area. CI fails when a generated
  file or PORTED is stale, or a PORTED line isn't one of its module's items: run `bun run gen` and commit.

## Notes

- The CLI (`src/cli/`) loads each command with a dynamic import, and `bun run compile` builds with `--bytecode` (so
  `src/main.ts` has no top-level await): `fleetd version` starts in 4.4 ms against 9.3 ms for the eager, parsed
  binary; an empty compiled Bun binary takes 1.4 ms and the Rust binary 0.2 ms (`bun scripts/startup.ts <binary>`).
- `test/cli/golden.test.ts` runs the Bun CLI and a Rust `fleetd` on the same inputs: with `FLEETD_RUST_BIN` set, every
  case live (the hub ones against a Rust hub on a scratch home); without it, the hub-free ones against
  `test/cli/fixtures/`, recorded with `RECORD=1`. Every call gets a scratch `FLEETD_HOME`, `HOME` and hub URL.
- `fleetd build-slot` takes the same flock(2) locks as the Rust one (through bun:ffi), so builds started by either wait
  for each other.

- tsc-rs 0.8.0 checks the whole tree, Bun's types and the 9k-line generated contracts included, with no fallback to
  tsc 7 needed so far.
- In a compiled binary the read worker is a second entry point (`--root .` keeps its path); `bun run smoke` runs the
  binary outside the source tree, so a worker left out of the build fails there rather than loading from disk.
- `await expect(promise).rejects…` never settled for a rejected `db.read()` on Bun 1.4.3; tests catch the rejection
  instead.
