# fleetd

The hub, the node and the CLI, in TypeScript on Bun (D342). TypeScript runs directly on Bun; the release form is one
file from `bun build --compile`; type checking is tsc-rs, a Rust port of tsc 7.

```sh
cd fleetd
bun install                # tsc-rs and Bun's types, pinned in bun.lock
bun run gen                # src/gen/migrations.ts, the docs pages generated from the code, the app's setup steps
bun run typecheck          # tsc-rs -p tsconfig.json
bun test
bun run compile            # dist/fleetd, one binary: fleetd hub start, fleetd node …, every other command
bun run smoke              # the binary end to end: version, hub start on a fresh home, /healthz, SIGTERM
bun run blackbox           # the binary as a user runs it (test/blackbox): closed pipes, homes, the installer, restarts
bun run check              # gen:check, typecheck, test, compile and smoke, as CI's `fleetd` job runs them
bun src/main.ts hub start --home "$TMPDIR/hub" --listen 127.0.0.1:4795   # from source
```

Never point it at the live hub's home or database: tests and runs use a fresh `--home` under `$TMPDIR`, and set
`FLEETD_HOME` too, so nothing reads `~/.fleetd`.

## Layout

| Path | What |
|---|---|
| `src/main.ts` | the binary's entry: `src/cli/index.ts` dispatches `hub start`, `node …` and the rest |
| `src/shared/contracts.ts` | the wire types, re-exported from the desktop app's `contracts.ts` (app/desktop/src/shared/contracts, with its JSON Schemas); never copy a type by hand |
| `src/shared/errors.ts` | `ToolError` (the contracts' `{ code, message, fix }`) and `NotImplemented` |
| `src/hub/store/` | `HubDb` over bun:sqlite: the migrations in `migrations/` run in order (`migrations_applied` keeps each one's SHA-256), WAL, and `db.read()` on a worker thread for long reads |
| `src/hub/auth/` | key checking (`fld_` keys by SHA-256, revocation on the next call) and the HTTP bearer check |
| `src/hub/api/` | `Hub` (the shared context; areas keep their services with `hub.area(name, make)`), the tool `Registry`, each tool's role (`tool_roles.ts`), grant checks |
| `src/hub/http/` | `Bun.serve` and the hub's routes; websockets pick their handler when they upgrade (`route.ts`) |
| `src/hub/serve/` | `fleetd hub start`: flags, build, serve, loops (`loops.ts`), every module's tools (`areas.ts`), stop on SIGTERM |
| `src/hub/prompts/defaults/` | the default prompts, one Markdown file each |
| `src/node/runner/host/` | a session's host, `fleetd session-host`: owns the session's claude, maps its stream-json, runs the kill ladder and the transcript, and outlives the node |
| `src/gen/` | generated by `scripts/gen.ts`; don't edit |
| `test/fixtures/` | recorded data the tests replay: claude's stream-json (`runner/`), sealed-box vectors, GitHub answers |

## How a module plugs in

- **Tools.** Every MCP tool in the contracts' `ToolMap` has its role and module in `src/hub/api/tool_roles.ts`, and is
  registered as a stub that answers `failed` until its module replaces it in `src/hub/<module>/tools.ts`:
  `export function register(tools: Registry) { tools.add("project_get", async (hub, caller, input) => …) }`. Input and
  output are typed from `ToolMap`; the registry checks the tool's role and decodes the input against its schema
  (McpTools.json) first. Throw a `ToolError` to refuse. A new module adds its `register` to `src/hub/serve/areas.ts`.
- **Lead calls.** A module answers its lead calls in `src/hub/<module>/calls.ts`:
  `leadCalls(hub).register("task_spawn", (caller, call) => …)` from its `loops.ts` `start(hub)` (src/hub/lead_calls).
  The call arrives decoded against its contract (the schema dir's LeadCall.json, kept out of the app's contracts.ts):
  types, brand patterns and bounds checked, defaults filled, unnamed fields dropped. `caller` is
  `{ projectRef, by, agent, threadId? }`, already attributed and through the policy; return the result without its
  `op` (the dispatch adds it), or throw a `ToolError` to refuse. The link answers each `lead_call` frame with
  `onLeadCallFrame(hub, machineId, frame, send)`.
- **Loops.** `src/hub/<module>/loops.ts` `start(hub)` starts the module's background loops; stop them on
  `hub.shutdown.signal`. A new module adds its `start` to `src/hub/serve/loops.ts`.
- **Routes.** A websocket route calls `upgrade(req, ctx, handler, state)`.
- **The database.** `hub.db.conn` is the bun:sqlite `Database` (opened `strict`: named parameters bind without their
  `$`); `hub.db.transaction(fn)` is `BEGIN IMMEDIATE`; `await hub.db.read(sql, params)` for a read that can take long.
  A new table is a new migration (docs/CONTRIBUTING.md).
- **The node link.** Its frames are typed in `src/shared/node_link.ts`; `src/shared/wire_tags.ts` lists its tags,
  session call ops, lead call ops and agent-mcp's tools.
- **Contracts.** A wire type changes in both `contracts.ts` and its JSON Schema; `test/contracts.test.ts` fails while
  they disagree.

## Notes

- The CLI (`src/cli/`) loads each command with a dynamic import, and `bun run compile` builds with `--bytecode` (so
  `src/main.ts` has no top-level await): `fleetd version` starts in 4.4 ms against 9.3 ms for the eager, parsed
  binary; an empty compiled Bun binary takes 1.4 ms (`bun scripts/startup.ts <binary>`).
- `test/cli/golden.test.ts` runs the CLI on fixed inputs, the hub ones against a hub on a scratch home, and compares
  each with `test/cli/fixtures/`, recorded with `RECORD=1`. Every call gets a scratch `FLEETD_HOME`, `HOME` and hub URL.
- `fleetd build-slot` takes flock(2) locks (through bun:ffi), so builds started by any fleetd on the machine wait for
  each other.
- tsc-rs 0.8.0 checks the whole tree, Bun's types and the 9k-line contracts included, with no fallback to tsc 7 needed
  so far.
- In a compiled binary the read worker is a second entry point (`--root .` keeps its path); `bun run smoke` runs the
  binary outside the source tree, so a worker left out of the build fails there rather than loading from disk.
- `await expect(promise).rejects…` never settled for a rejected `db.read()` on Bun 1.4.3; tests catch the rejection
  instead.
